## 1. Channel-aware генерация workflow-графа (#6) — BIG

**Текущее состояние.** `createTemplate(signalType, sourceType)` (`src/state/workflow-templates.ts:297`) полностью игнорирует выбранные каналы: берёт фиксированный per-signal-type шаблон из `TEMPLATE_BY_TYPE` (`:254`), опционально вставляет ноду скоринга (`withScoring`, `:270`). 6 шаблонов хардкодят свои коммуникационные ноды (registration → email+push; first-deal → sms; reactivation → sms+ivr и т.д.). Ни один шаблон не читает `channels`. Вызовы: `workflow-view.tsx:63` (живой граф канваса — главный потребитель), `campaign-graph-cost.ts:25`, `campaign-payment-screen.tsx:78`, `workflow-mini-preview.tsx:34`.

**Проблема (из aim #6).** Пользователь выбрал на шаге «Каналы» SMS и IVR, но в сгенерированном воркфлоу их нет — граф собран по фиксированному шаблону, а не по выбору.

**Намерение.** Генерация графа должна ориентироваться (а) на выбранные `campaign.channels`/`StepData.channels` и (б) на набор правил (структура: Сигнал → [Скоринг] → коммуникации → результат), подставляя коммуникационные ноды по выбранным каналам.

**Ключевые развилки (решить в своём брейншторме):**
- Шаблон задаёт только структурный скелет (Сигнал/Скоринг/Условие/Результат), а коммуникационные ноды генерируются из `channels` — или остаются именованные per-scenario пресеты, переопределяемые каналами?
- Порядок/ветвление нескольких каналов: цепочкой, параллельно (split), или по условию? Нужны ли «правила» (например, IVR после SMS-недозвона)?
- Как это бьётся со сходимостью цен (граф уже единый источник стоимости — batch 2 F): смена каналов меняет граф → меняет цену; убедиться, что обе поверхности (визард/оплата) пересобирают граф с одинаковыми каналами.
- Дедупликация: `defaultParamsFor` (`structural-commands.ts:330`) и `defaultParams` (`rebuild-schema.ts:31`) дублируют per-channel дефолты — свести в одну channel→node-builder карту (возможно новый `channel-nodes.ts`), переиспользуя `CHANNEL_LABEL` и `NODE_STYLES`/`getNodeColor` (`node-visuals.ts`).

**Рекомендуемый подход.** Ввести `channels` третьим аргументом `createTemplate` (и прокинуть из всех 4 вызовов); вынести channel→node маппинг в один модуль; шаблон оставить как структурный скелет, коммуникации строить из каналов. Покрыть тестами генерацию по разным наборам каналов + сходимость цен.

**Оценка:** крупно — движок генерации + 4 вызова + цена + тесты.

## 2. AI-редактирование графа: ветки/условия вместо плоской цепочки (#7) — BIG

**Текущее состояние.** Через промпт-бар AI правит граф двумя путями:
- `rebuild_workflow` (`rebuildGraphSchema`, `rebuild-schema.ts:19`): `{ nodes:[{key,nodeType,label,sublabel?}], edges:[{from,to,label?}], assumptions }`. Схема УЖЕ поддерживает ветки (произвольные `from→to` + label YES/NO, `nodeType` включает condition/split/merge). НО `buildGraphFromSpec` (`:54`) раскладывает все ноды линейно (`x: STEP*(i+1), y: end?120:0`, `:71`) независимо от топологии рёбер → выглядит плоско; `relayoutGraph` на rebuild НЕ вызывается.
- `edit_workflow` (`wireOpSchema`, `ops-wire-schema.ts:11`): плоские операции add/remove/replace с `placementMode: after|before|between|auto` — все делают одиночную врезку по ребру, НЕТ операции «добавить условие с двумя ветками».

**Проблема (из aim #7).** AI умеет делать только плоскую структуру (одна нога за другой); хочется, чтобы он понимал намерение сделать сложную (ветвящуюся) структуру.

**Намерение.** AI через промпт-бар строит и редактирует нелинейные графы (условия с YES/NO ветками, split/merge).

**Ключевые развилки:**
- Починить layout rebuild: заменить линейную раскладку в `buildGraphFromSpec` на BFS-колоночную (уже есть `relayoutGraph`, `structural-commands.ts:696`) — вызвать её на пересобранном графе. Это даёт визуальные ветки из уже эмитируемых рёбер.
- Расширить `edit_workflow`/`StructuralOp` ветка-осведомлённой операцией (добавить condition + две ветки; или таргетить конкретное исходящее ребро по label).
- Промпт: контекст графа в `orchestrator-prompt.ts:33` отдаёт только `from → to` без меток рёбер — AI не видит существующие ветки. Добавить метки рёбер (YES/NO) в контекст.

**Рекомендуемый подход.** Начать с layout-фикса rebuild (дёшево, сразу даёт ветки из rebuild) → затем метки рёбер в промпт → затем branch-aware edit-операции. Возможно разбить на под-итерации.

**Оценка:** крупно — схема + layout + apply-семантика + промпт, скоординированно.

## 3. AI-ровер сборки шаблона диалогом (#15) — MEDIUM→BIG

**Текущее состояние.** «Создать шаблон вручную» (`templates-tab.tsx:29`) сейчас просто диспатчит `start_campaign_flow` (открывает визард) — никакого создания шаблона. Шаблоны не создаются в рантайме: `templates` сидируется из `PRESET_TEMPLATES` (`app-state.ts:108`); **нет экшна `template_added`** (единственное касание `templates` — инкремент `usedInCampaigns` в `campaign_launched`, `:901`). `MessageTemplate = { id, channel, name, content: NodeParams, usedInCampaigns }` (`:93`).

**Проблема/намерение (из aim #15).** Клик по «Создать шаблон» открывает AI-ровер (drawer), который ведёт диалог: (1) какой тип коммуникации (канал) → (2) какой месседж хотят донести → предлагает варианты → по завершении закрывает ровер и добавляет новый шаблон в список.

**Ключевые развилки:**
- Многошаговый guided-диалог: новый паттерн. Ближайшее существующее — tool `clarify` (`route.ts:77`, один раунд ≤2 вопросов) + `EmailEditorState`/`open_email_editor` (`chat-context.tsx:34,62`) как образец drawer-side AI-сборки. Полноценной многоходовой оркестрации «канал → интент → варианты» пока нет — её логика новая.
- Нужен новый reducer-экшн `template_added` (+ `MessageTemplate` в стейт) и новый orchestrator-tool `create_template` + новый `AssistResult` kind (`assist-contract.ts:50`).
- Где открывается ровер: `chat-context.tsx` `openSidebar()`/`ChatPanelMode "sidebar"`, `chat-drawer.tsx`. Учесть авто-закрытие drawer на смене scope (`resetChat`).

**Рекомендуемый подход.** Отдельный цикл: спроектировать guided-flow (состояние диалога + tool + result kind), reducer `template_added`, и UX ровера. Переиспользовать email-editor паттерн как основу.

**Оценка:** средне-крупно — новый экшн + tool оркестратора + многошаговое состояние диалога.
