## 1. Контекст и цель

Полировочный проход по прототипу Afina (Next.js 16, Tailwind v4, motion v12). Цель — три
независимые области правок, объединённые в одну спеку и один план реализации:

- **A. Мастер создания сигнала** — переименование экрана обогащения, порядок шагов.
- **B. Промпт-бар** — иконка drawer, унификация компонента, перекрытие контента.
- **C. Поля нод** — визуальное разделение редактируемых/AI-полей, каталог полей.

Прототип валидирует UX на реальных пользователях — поведение важнее перформанса.

## 4. Область A — Мастер создания сигнала

### Текущее состояние

Создание сигнала запускается экшеном `start_signal_flow` из 4 точек (секция «Сигналы»,
карточки онбординга, онбординг-чат ×2) — все ведут в `GuidedSignalSection`. Та показывает
анкету `SurveySection` (ввод сайта → экран обогащения) **только при первом запуске**
(`surveyStatus !== "completed"`), затем — визард `CampaignWorkspace` со степпером
`CampaignStepper`.

Степпер начинается с пункта «Интересы» (`step: 2`); экран `Step1Scenario` («Выберите тип
сигнала») рендерится в визарде, но **в степпере не представлен** и сам степпер появляется
только при `currentStep >= 2`. Для пользователя это читается как «визард начинается с
интересов».

### Задача 1 — переименование экрана обогащения

Файл `sections/survey/survey-awaiting.tsx`:
- Заголовок «Анализируем сайт» → **«Обогащение данными»**.
- Подзаголовок «Изучаем {сайт} и подбираем интересы» → формулировка без слова «интересы»
  (интересы выбираются позже, на отдельном шаге). Рабочий вариант:
  «Изучаем {сайт} и дополняем профиль компании», фолбэк без хоста — «Дополняем профиль
  компании данными». Точная формулировка финализируется при реализации (задача это
  допускает явно).

Прогресс-бар, тайминги, анимация — без изменений.

### Задача 2 — порядок флоу

**2a. Сайт — этап непосредственно перед выбором типа сигнала.**

Сайт спрашивается **один раз за сессию** (за загрузку приложения). Этот экран — пред-шаг
к шагу «Тип сигнала» в флоу создания сигнала; повторно за сессию сайт не спрашивается.

Дизайн:
- Текущий гейт `GuidedSignalSection` уже даёт это поведение: пока сайт за сессию не
  введён (`surveyStatus !== "completed"`), перед визардом показывается `SurveySection`
  (ввод сайта → экран обогащения); после — визард открывается сразу на шаге «Тип
  сигнала».
- Задача — убедиться, что во всех точках входа в создание сигнала экран сайта/обогащения
  стоит именно как пред-шаг к «Тип сигнала» и «Тип сигнала» не достигается без введённого
  за сессию сайта; при расхождении — поправить проводку гейта.
- Поле сайта в `SurveyForm` предзаполняется сохранённым `survey.companyWebsite`.
- **Resume-флоу — исключение:** возобновление существующего сигнала (`activeResume`
  задан) пропускает экран сайта — визард открывается на сохранённом шаге.
- `surveyStatus` остаётся механизмом «сайт за сессию введён». `SurveySection` на этом
  входе — `skippable={false}` (сайт обязателен).

**2b. «Тип сигнала» — первый шаг степпера.**

- В `STEPPER_ITEMS` (`campaign-stepper.tsx`) добавить первым элементом
  `{ label: "Тип сигнала", step: 1 }`. Нумерация в степпере идёт по `idx + 1`, поэтому
  пункты автоматически перенумеруются: Тип сигнала = 1, Интересы = 2, …, Результат = 8.
- В `campaign-workspace.tsx` условие показа степпера `currentStep >= 2` → `currentStep >= 1`.
- Проверить раскладку: степпер позиционируется `absolute top-6 right-…`; на шаге 1
  (`Step1Scenario`, сетка `grid-cols-3`) убедиться, что степпер не перекрывает контент —
  при необходимости поправить отступы шага.

### Итоговый флоу

**Сайт → Обогащение данными → [степпер: 1 Тип сигнала · 2 Интересы · 3 Сегменты ·
4 База · 5 Бюджет · 6 Сводка · 7 Обработка · 8 Результат].** Сайт + обогащение — один раз
за сессию, как пред-шаг к «Тип сигнала».

Интересы и триггеры остаются на одном шаге (как сейчас) — разделять не требуется.

## 5. Область B — Промпт-бар

### Текущее состояние — ключевое

В проекте **две независимые реализации промпт-бара**:

1. **`ShellBottomBar`** (`sections/shell/shell-bottom-bar.tsx`) — на всех экранах, кроме
   создания сигнала. `fixed`-карточка `rounded-[34px] p-6`, **без шапки**, без лейбла
   «Афина ИИ», без кнопки drawer. Содержит `ChipEditableInput`, кнопку микрофона, сабмит,
   условные чипсы (онбординг, кампании, помощь по бюджету). Несёт пер-вью роутинг сабмита
   (welcome-чат, фильтр кампаний, команды воркфлоу) и зеркалит выбранную ноду в чип.
2. **`ChatPanel`** (`sections/shell/chat-panel.tsx`) — только на экране создания сигнала.
   Два режима: `collapsed` (нижний бар `rounded-[16px] p-3`) и `sidebar` (правый drawer,
   420px). В `collapsed` есть шапка `ChatPanelHeader` (иконка-маскот + «Афина ИИ» + кнопка
   `Maximize2`), `TransientReply`, `ChatComposer`. Несёт историю чата, mock-ответы AI,
   интеграцию с trigger-edit.

`page.tsx`: `view.kind === "guided-signal" ? <ChatPanel/> : <ShellBottomBar/>`.

### Задача 3 — иконка открытия drawer

Файл `chat-panel-header.tsx`: иконка `Maximize2` → `PanelRightOpen` (`lucide-react`).
Кнопка уже семантически «Открыть в drawer» (`aria-label="Открыть в drawer"`,
`onClick={onOpenSidebar}`) — меняется только иконка. После задачи 4 эта же иконка едет в
шапку единого `PromptBar`.

### Задача 4 — единый компонент промпт-бара

**Подход (согласован): общая обёртка `PromptBar`.**

Создаётся компонент `PromptBar` — визуальная обёртка промпт-бара:
- Внешняя фростед-карточка (единый радиус/паддинг — по умолчанию значения `collapsed`
  `ChatPanel`: `rounded-[16px]`, фон `rgba(10,10,10,0.75)`, `backdrop-blur`; финальные
  числа — при реализации).
- Шапка-стрип: `mascot-icon.svg` + лейбл «Афина ИИ» + кнопка открытия правого drawer
  (`PanelRightOpen`).
- Слот `children` — для инпута/футера/чипсов конкретного экрана.

И `ShellBottomBar`, и `collapsed`-режим `ChatPanel` рендерят свой инпут **внутрь**
`PromptBar` через `children`. Обёртка одинакова на всех экранах; экранная логика (роутинг
сабмита, чипсы, история чата) остаётся в своих компонентах — это не сливается, чтобы не
рисковать регрессиями в роутинге команд.

**Глобальный drawer (согласовано).** Правый AI-drawer становится доступен с любого
экрана:
- Drawer-хост (`ChatPanel` в режиме `sidebar` либо выделенный компонент-хост) поднимается
  на уровень шелла в `page.tsx` и рендерится для всех `view.kind`, а не только
  `guided-signal`. `ChatProvider` уже обёрнут вокруг всего дерева в `page.tsx` — состояние
  чата доступно глобально.
- Кнопка `PanelRightOpen` в шапке `PromptBar` открывает drawer на любом экране.
- `page.tsx` всегда рендерит единый промпт-бар + глобально доступный drawer; ветка
  `guided-signal ? ChatPanel : ShellBottomBar` убирается в пользу общей композиции.

**Экраны промпт-бара** (перечень из кода — на каждом единый `PromptBar`): welcome,
создание сигнала (`guided-signal`), секции «Сигналы» / «Кампании» / «Статистика`,
`workflow`, `campaign-select`. Плейсхолдер инпута остаётся пер-вью (через проп) — это
не нарушает единство обёртки.

> Примечание по задаче из источника: «Companies» в задаче 4 трактуется как реальные
> экраны прототипа — секции «Сигналы», «Кампании», «Статистика» и прочие, где промпт-бар
> уместен. Отдельного экрана «Компании» в коде нет.

Реконсиляция двух тел (`ShellBottomBar` vs `collapsed` `ChatPanel`) и точная проводка
глобального drawer — основной объём имплементации; решается в плане, опираясь на
`docs/promptbar-drawer-mehanika.md`.

### Задача 5 — перекрытие скроллируемого контента

**Правило (рабочий паттерн, применять везде):** нижний промпт-бар никогда не перекрывает
скроллируемый контент. Каждый скроллируемый контейнер получает `padding-bottom` не меньше
полной высоты **обёртки** промпт-бара (от верхнего края обёртки, не инпута) плюс запас на
тень/отступ.

Текущий разнобой: `pb-40`, CSS-переменная `--promptbar-height` (её выставляет только
`ShellBottomBar` через `ResizeObserver`; `ChatPanel` — нет), хардкод-фолбэки `220px` /
`140px`.

Дизайн:
- Единый `PromptBar` **всегда** выставляет `--promptbar-height` через `ResizeObserver`
  (одно место — в обёртке).
- Вводится токен запаса `--promptbar-gap` (ориентир 16–24px).
- Все скроллируемые контейнеры используют
  `padding-bottom: calc(var(--promptbar-height) + var(--promptbar-gap))` через единую
  Tailwind-утилиту/класс (напр. `pb-promptbar`).
- Контейнеры к правке (перечень из кода): `campaign-workspace` (сейчас `pb-40`),
  `welcome-view`, `signals-section`, `campaigns-section`, `workflow-section`,
  `statistics-view`. Хардкод-фолбэки `220px`/`140px` убираются.

## 6. Область C — Поля нод

### Текущее состояние

В `types/workflow.ts` — 18 типов нод; у 13 есть схема `NodeParams`, у 5 «легаси»-типов
(`default`, `channel`, `retarget`, `result`, `new`) схемы параметров нет (используются в
базовом графе и парсере команд). Поля ноды рендерятся read-only в `NodeCardBody`
(`node-card-content.tsx`) через карту `PARAM_RENDERERS` → `getParamRows`. Инлайн-
редактирования нет: клик по строке параметра вставляет шаблон из `NODE_ACTIONS` в
промпт-бар; внизу карточки — подпись «Изменить через промпт ниже».

### Принцип (из источника)

У ноды есть поля, легко редактируемые вручную (интерактивные текстовые поля), и поля,
вшитые глубоко в систему (заголовки, deep-ссылки) — их нельзя править руками, только
через AI, чтобы не ломать связи (safe rails). Оба типа полей **не делятся на отдельные
секции** — они часть настроек одной ноды и стоят вместе. Разница — только в способе
редактирования.

### Задача 7 — каталог полей (делается первой)

Полный каталог типов нод и их полей с пометкой способа редактирования —
**Приложение A**. Каталог построен по `NodeParams` (`workflow.ts`) и `PARAM_RENDERERS`
(`node-card-content.tsx`). Категории:

- **Вручную** — карандаш, поле становится текстовым инпутом.
- **Только AI** — иконка-ассистент, тег поля улетает в промпт-бар.
- **Нередактируемое** — вычисляемые/системные значения, только показ.

Каталог в Приложении A — **черновик на утверждение**. Ревью этой спеки пользователем и
есть точка утверждения каталога перед версткой задачи 6. Спорные поля помечены ⚠.

### Задача 6 — визуальное разделение полей

В пределах одной ноды оба типа полей идут вместе, без деления на секции. Различие — иконка
рядом с полем (в `NodeCardBody`):

- **Поле, редактируемое вручную:**
  - Иконка-карандаш (`Pencil`, lucide) рядом с полем.
  - Клик по иконке → значение поля превращается в обычный текстовый инпут.
  - Пользователь правит → подтверждает галочкой (`Check`) или Enter → диспатчится
    обновление параметров (через паттерн `patchNodeParams`).
- **Поле, не редактируемое вручную:**
  - Иконка-ассистент (маскот / AI-индикация) вместо карандаша.
  - Клик по иконке → тег поля улетает в промпт-бар, работа продолжается через AI
    (механика чипа, аналогично текущему `node`-чипу, но для конкретного поля).
- **Нередактируемое поле** (если по каталогу есть) — без интерактивной иконки, только
  показ значения.

Изменения в `NodeCardBody`: убрать общий «клик по строке → вставка шаблона» и подпись
«Изменить через промпт ниже»; вместо этого — по-польные иконки и инлайн-инпут для ручных
полей. `NODE_ACTIONS` переиспользуется для AI-полей (что улетает в бар).

Реализуется **после** утверждения каталога (Приложение A).

## 7. Тестирование

Проект на Vitest (база — 265 тестов, 19 файлов, всё зелёное). Подход — компонентные/
юнит-тесты на ключевое поведение:

- **A:** степпер содержит «Тип сигнала» как пункт 1; визард показывает экран сайта перед
  «Тип сигнала», пока сайт за сессию не введён, и пропускает его на resume-флоу;
  `survey-awaiting` показывает новый заголовок.
- **B:** `PromptBar` рендерит шапку (маскот + «Афина ИИ» + кнопка drawer); кнопка drawer
  открывает sidebar на не-`guided-signal` вью; `--promptbar-height` выставляется единым
  баром.
- **C:** `getParamRows` без регрессий; `NodeCardBody` рендерит корректную иконку
  (карандаш/ассистент) по каталогу; инлайн-правка ручного поля диспатчит обновление
  параметров.

Обработка ошибок — минимальная (прототип): валидация сайта остаётся на `isWebsiteValid`;
крайние случаи AI описываются по минимуму.

После каждой фазы — `npm test` и `npm run lint` зелёные. Dev-сервер на 3000 держит
пользователь; параллельный воркспейс при необходимости поднимает dev на `-p 3001`.

18 типов нод. У 5 легаси-типов (`default`, `channel`, `retarget`, `result`, `new`)
схемы `NodeParams` нет — редактируемых полей нет, в каталог по полям не входят. Ниже —
13 типов со схемой параметров.

Легенда: ✏️ вручную · 🤖 только AI · 🔒 нередактируемое · ⚠ спорное (решить на ревью).

### Logic / Flow

**`split` — Split по сегментам**
| Поле | Лейбл | Тип | Способ |
|------|-------|-----|--------|

| `branches` | Ветки | number | 🤖 ⚠ — число веток меняет граф; ручной ввод может оторвать рёбра |

**`wait` — Ожидание**
| Поле | Лейбл | Тип | Способ |
|------|-------|-----|--------|

| `durationHours` | Длительность | number? | ✏️ ⚠ — число; править можно, но валидно лишь при `mode=duration` |
| `untilEvent` | Событие | string? | 🤖 — идентификатор системного события |

**`condition` — Условие**
| Поле | Лейбл | Тип | Способ |
|------|-------|-----|--------|
| `trigger` | Триггер | enum (6 значений) | 🤖 — enum доставки/реакции, не свободный ввод |

**`merge` — Merge** — полей нет.
