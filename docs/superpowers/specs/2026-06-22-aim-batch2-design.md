## D. Интересы + триггеры — полный возврат старого шага (#6, #10)

Старый `src/sections/campaigns/wizard/steps/step-2-interests.tsx` (~800 строк) цел в дереве, но не смонтирован. Текущий лёгкий `step-interests.tsx` его заменяет в `campaign-workspace`.

- **Вернуть `Step2Interests`** как компонент шага `"interests"` в `campaign-workspace.tsx` `renderStepContent` (вместо `StepInterests`). Полный функционал: по-интересные триггеры (`Interest.triggers`), `TriggerCard` (выбор/раскрытие/домены), add/exclude доменов (`TriggerDelta`, `SystemDomainChip`, `DeltaChip`), AI-бридж (`useRegisterTriggerEdit`, `pushSectionChip`), seeded-префилл (`initialPrefill` — 3 интереса + до 5 триггеров по `clientDirection`), ремикс по `wizardRemixToken`.
- **Контекст-провайдеры:** `Step2Interests` зависит от trigger-edit и prompt-chips контекстов. Убедиться, что они смонтированы вокруг визарда (в `guided-campaign-section` / `app/page.tsx` / шелле). Если нет — обернуть хост визарда нужными провайдерами. Проверить на этапе плана точные имена провайдеров и где монтировать.
- **Персистенция:** `Step2Interests.handleContinue` уже сериализует `interests` + `triggers` + `triggerConfig` в `StepData` через `onNext` — совместимо с текущей моделью.
- **Префилл (#10):** обеспечивается `initialPrefill` (по направлению). Связь «сценарий → интересы» НЕ вводим (решение брейншторма — переиспользуем direction-префилл).

## F. Сходимость цен визард ↔ оплата (#14)

Проблема: визард считает по плоской модели (`estimateCampaignBudget`: каналы×база×1.3), оплата — по графу (`computeCampaignCost` с воронкой). Расхождение на порядок (~1.2М vs 766к).

**Решение (графовый расчёт везде):**
- Шаг «Бюджет» визарда переводится на тот же путь, что экран оплаты: строит граф через `createTemplate(scenarioSignalType, sourceType)` (где `scenarioSignalType = getScenario(data.scenario)?.signalType`) и считает `computeCampaignCost(graph.nodes, graph.edges, audienceSize)`. `audienceSize` — та же база, что использует оплата (`data.fileRowCount ?? FALLBACK_BASE`).
- Разбивку «Сигналы/Коммуникация/Итого» в визарде берём из `CampaignCost` (как на оплате: `cost.total`, `cost.lines`, `cost.repeat`), а не из `estimateCampaignBudget`.
- На экране оплаты привести «Платежи»-блок и «Из чего складывается» к одному источнику (`computeCampaignCost`), чтобы внутри экрана тоже не расходились (сейчас «Платежи» использует плоский `splitCampaignPayments`, а «Из чего складывается» — граф).
- Дневной бюджет для `stream` — сохранить (производное от total).
- Пропорциональный пересчёт «Своя сумма» (из прошлого батча, `scaleBreakdown`) — оставить поверх графовых строк.

**Оговорка (известное упрощение):** шаблон графа задаёт набор каналов по сценарию/типу сигнала, а не по выбору пользователя на шаге «Каналы». Выбор каналов в граф НЕ прокидываем в этом батче (вне scope). Цель правки — сходимость двух экранов, а не точность по выбранным каналам; обе цифры теперь из одной графовой модели → сходятся.

**Не трогаем** `estimateCampaignBudget`/`splitCampaignPayments` как код (могут остаться для других мест), но визард и оплата на них больше не опираются для головных цифр. Если после миграции они становятся мёртвыми — удалить (проверить ссылки).

## G. Поток запуска + гейты (#11, #12, #13)

Сейчас: финиш визарда → `campaign_created_from_wizard` → `status:"draft"` + `view:{kind:"workflow"}` (workflow-редактор). Запуск позже с карточки → `open_campaign_payment` → оплата → `campaign_launched`. Сбор сигналов (scoring) — только ПОСЛЕ `campaign_launched` (для `new`).

**Новая модель (пред-запусковый сбор для `new`):**
- **Финиш визарда** (`campaign_created_from_wizard`): создаёт кампанию `status:"draft"` и открывает её **карточку** (`view:{kind:"campaign"}`), а НЕ workflow-редактор.
- **Сбор сигналов как пред-запусковая фаза:**
  - `new` → на карточке сразу идёт **сбор сигналов**: визуал `CampaignSignalProgress` (старый «обработка базы», 4 шага, ProviderList, % бар). Завершается через прежнее окно (`SCORING_WINDOW_MS`) → артефакт собран (по логике campaign-first батча `campaign_phase_advanced`/генерация артефакта). До завершения сбора кнопка **«Запустить» заблокирована**.
  - `stream` / `own` → сбора нет; **«Запустить» доступен сразу**.
  - Состояние сбора моделируем на draft-кампании: переиспользовать поле `phase` («scoring» во время сбора, «communicating»/готово после) ИЛИ эквивалентный флаг — точную форму выбрать на этапе плана так, чтобы `CampaignSignalProgress` и гейт «Запустить» читались консистентно и не конфликтовали с пост-launch семантикой `campaign_launched`. Ключевой инвариант: сбор идёт на ПРЕД-запусковой (draft) кампании; артефакт = собранные сигналы; «Запустить» = запуск коммуникации (оплата) поверх собранного артефакта.
- **«Запустить» на карточке:**
  - `new` → виден/активен только после завершения сбора; клик → `open_campaign_payment`.
  - `stream`/`own` → активен сразу; клик → `open_campaign_payment`.
- **Гейт по балансу (#11):** на экране оплаты уже есть `computeShortfall`/`enoughBalance` (кнопка «Пополнить и запустить» + инлайн-подсказка «Не хватает ₽N» из прошлого батча). Подтвердить, что запуск невозможен при нехватке (модалка пополнения вместо запуска). Дополнительно — НЕ блокировать сам сбор сигналов по балансу (сбор для прототипа стартует бесплатно; оплата — за коммуникацию).

**Влияние:** меняется `campaign_created_from_wizard` (роут + инициализация фазы по источнику), `campaign-screen.tsx` (условие показа `CampaignSignalProgress` на draft + гейт «Запустить» по источнику/фазе), возможно reducer-экшены фазы. Это самая тяжёлая часть — изолировать и покрыть тестами (reducer-переходы + гейт).

## Порядок и границы

- **Лёгкие сначала:** A (переименование), B (каталог), E (копи бюджета) — низкий риск.
- **Средние:** C (рекомендация источника), F (графовая сходимость цен).
- **Тяжёлые в конце:** D (полный step-2 + провайдеры), G (реформа потока + пред-запусковый сбор + гейты). G делать последним — он трогает reducer и карточку.
- **Не трогаем:** логику артефактов сверх перечисленного; набор каналов в графе (оговорка F); reflex-списки шрифтов и т.п.
