# Спека: последовательный прогресс кампании после запуска

Дата: 2026-07-07
Статус: утверждён дизайн, готов к плану реализации

## Проблема

Карточка кампании сразу показывает этап «Коммуникация по сигналам» вместо
последовательной обработки. Сейчас модель прогресса двухфазная (`phase:
"scoring" | "communicating"`), а «Обработка базы» — это ПРЕД-лонч сбор у нового
черновика (`isCollecting`), который гейтит «Запустить». После запуска кампания
становится `communicating` мгновенно.

## Цель

После запуска кампания проходит этапы **по очереди во времени**:

```
Отправка провайдерам → Проверка провайдерами → Обработка базы → Коммуникация по сигналам
     (8с)                    (8с)                  (30с)              (терминальный)
```

- В «Обработке базы» показывается распределение сигналов/день по операторам
  (существующий `ProviderList`, провайдеры подключаются 6/14/23с, Tele2 застревает).
- **Артефакт** (файл с сигналами) появляется только ПОСЛЕ «Обработки базы».
- **Статистика** (отправки/клики/действия/CR) — пустая (нули/«—») пока не
  началась «Коммуникация»; затем наполняется.

## Решения (из брейншторма)

1. **Модель — от времени запуска.** Текущий этап вычисляется от `launchedAt` +
   прошедшее время. Свеже-запущенная кампания шагает по этапам; запущенная давно
   (сиды/старые) уже прошла всё → коммуникация + статистика + артефакт. Переживает
   уход/возврат (не сбрасывается).
2. **Пред-лонч сбор убираем.** Черновик готов к запуску сразу (по валидности
   графа). Вся последовательность (вкл. обработку базы) играет ПОСЛЕ запуска.
   Удаляем `isCollecting`/`SCORING_WINDOW`-пред-лонч.
3. **Тайминг:** отправка 8с + проверка 8с + обработка 30с. Коммуникация ≈ через
   46с после запуска.
4. **Все типы источника.** Обобщаем по этапам, которые есть у типа:
   - не-stream: `send → verify → process → communicate` (или `done` для no-comm);
   - stream: `connect → process` (у stream «process» = «Обработка и коммуникация»
     — обработка и коммуникация вместе).
5. **Статистика до коммуникации — показывать с нулями/«—»** (не прятать секцию).

## Подход (A: чистая функция + хук-часы)

Этап выводится чистой функцией от `launchedAt`; хук перерисовывает карточку на
границах этапов; персистентную часть (артефакт + переход фазы) ставит один
пост-лонч таймер через существующий `campaign_phase_advanced`. Минимум нового
стейта, ядро логики — чистое и тестируемое.

## Архитектура

### 1. Ядро — время → этап (`campaign-progress.tsx`, чистое, без таймеров)

Длительности по id этапа:

```ts
const STAGE_DURATION_MS: Record<string, number> = {
  send: 8000, verify: 8000, connect: 8000,
  process: 30000,
  // терминальные (communicate, done) — без длительности, остаются текущими
};
```

- `campaignStageAt(stages, elapsedMs): number` — аккумулирует длительности
  этапов; возвращает индекс текущего этапа. Терминальный (последний
  `communicate`/`done`) — как только elapsed ≥ суммы длительностей предыдущих.
- `communicatingThresholdMs(stages): number` — момент старта коммуникации =
  кумулятивная длительность до этапа коммуникации:
  - не-stream: `send + verify + process` = 46000;
  - stream: `connect` = 8000 (process у stream — уже коммуникация).
- Существующий `campaignProgressStages(c)` продолжает отдавать СПИСОК этапов;
  `currentIndex` теперь берётся из `campaignStageAt` для запущенной кампании
  (а не из `phase`). `status: "completed"` → `currentIndex = stages.length`
  (все done). `paused` → замороженный индекс (см. часы).

### 2. Часы — `useCampaignClock(campaign)` (новый хук)

- Считает `elapsedMs`:
  - `active`: `now − launchedAt`;
  - `paused`: `pausedAt − launchedAt` (заморожено);
  - `completed`: `Infinity` (всё done);
  - `draft`: не используется (степпер не показан).
- Ставит `setTimeout` до следующей границы этапа (и до порога коммуникации),
  затем форсит перерисовку — так текущий этап и провайдеры обновляются вживую.
  Без тика каждую секунду (только границы).
- `Date.now()` берём в компоненте/хуке (доступно; запрещено только в
  workflow-скриптах).

### 3. Запуск (app-state, `campaign_status_changed → active`)

- Уже ставит `status: "active"` + `launchedAt`. Добавляем `phase: "scoring"`
  (старт последовательности). Пред-лонч сбор удаляется — черновик не «собирает».
- «Запустить» доступна для валидного черновика сразу (гейт графа не трогаем).

### 4. Пост-лонч переход фазы (карточка)

- Один `useEffect`-таймер: если `active && phase === "scoring"` и
  `elapsed < communicatingThresholdMs`, ставим `setTimeout` на остаток →
  `dispatch(campaign_phase_advanced)` (существующий редьюсер: `phase →
  communicating` + создаёт артефакт + бейдж сигналов).
- Если `elapsed ≥ threshold` (старая кампания) — таймер не нужен, состояние уже
  корректно (у сидов phase communicating + артефакт заданы).
- Заменяет удаляемый пред-лонч `SCORING_WINDOW`-таймер.

### 5. Гейты (карточка / блоки)

- **Провайдеры** — под текущим этапом `process` (без изменений: `isProcess &&
  status === "current"` → live `ProviderList`; `done` → settled strip).
- **Артефакт** — секция только `campaignArtifacts.length > 0` (убираем
  `|| collectingNow`). Артефакт создаётся на пороге коммуникации → до него нет.
- **Статистика** — секцию показываем для `active || completed` (как сейчас), но
  `CampaignStatsBlock` получает флаг `populated = (phase === "communicating") ||
  completed`. При `populated === false` рендерит нули/«—» для отправок/кликов/
  действий/CR (метрики видны, но пустые). При `true` — реальные значения.
