## 3. Модель сценария

Сценарий — бизнес-цель пользователя; под ней готовая связка **Сигнал** (триггеры/интересы,
поставщики данных скрыты) + **Кампания** (каналы/креативы). Пользователь видит именованный
путь с описанием бизнес-цели.

```ts
type ScenarioCategory =
  | "Привлечение" | "Онбординг" | "Апсейл" | "Удержание" | "Возврат" | "Реактивация";

interface Scenario {
  id: string;
  name: string;            // именованный путь
  description: string;     // одно предложение — бизнес-цель
  category: ScenarioCategory;
  signalType: SignalType;  // тип под капотом — даёт предзаполнение шага 2 + workflow-шаблон
  isBase: boolean;         // один из 6 «Базовых сценариев»
  isCurated: boolean;      // показывается в секции «Подобрано для вас»
}
```

- Статичная библиотека **24 сценария** (Приложение A). `N = scenarios.length` — одно число
  во всех текстах: «Нашли N», «Подобрано N», «Все N».
- **6 базовых сценариев** = 6 типов сигнала 1:1 (Регистрация / Первая сделка / Апсейл /
  Удержание / Возврат / Реактивация). `signalType` базового сценария совпадает с его сутью.
- **«Подобрано для вас»** — 4 не-базовых сценария с `isCurated: true`.
- Откуда берётся библиотека — для прототипа неважно; список захардкожен.
- Выбор сценария → визард использует `signalType` для предзаполнения шага 2 (существующая
  seeded-логика) и для workflow-шаблона. «Магия под капотом»: пользователь видит сценарий,
  система знает тип.

## 4. Блок 1 — онбординг, каталог, шаг 1

### 4.1. Онбординг — 3 экрана

Переделка `sections/survey/`. Гейт — `surveyStatus` (механизм «онбординг пройден за
сессию»). Чат-бот на онбординге **скрыт**. Тон — профессиональный, тёплый, на «вы»;
третий экран — эмоциональный пик. Онбординг **опциональный**: «Пропустить» доступно.

**Экран 1 — ввод сайта.** Из `SurveyForm`.
```
Заголовок:    Расскажите о вашей компании
Подзаголовок: Введите адрес вашего сайта, чтобы мы подобрали сценарии под ваш бизнес.
[ Поле ввода: адрес сайта ]   [ Продолжить → ]   [ Пропустить ]
```

**Переход 1→2.** Короткая анимация «Обогащение данными» (из `SurveyAwaiting`) — прогресс,
тайминги, анимация без изменений.

**Экран 2 — подтверждение интересов.** Система показывает определённые по сайту тематики;
пользователь убирает лишнее / добавляет своё (редактируемые чипсы).
```
Заголовок:    Уточним детали
Подзаголовок: Это направления, которые мы определили. Поправьте, если что-то не так.
[ Чипсы интересов — редактируемые ]   [ Продолжить → ]
```

**Экран 3 — «Нашли сценарии» (эмоциональный пик).**
```
Заголовок:    Мы нашли [N] сценариев специально для вас
Подзаголовок: Каждый сценарий — готовая связка сигнала и кампании, адаптированная под
              ваш бизнес.
[ Выбрать сценарий → ]
```
Клик «Выбрать сценарий» → модалка «Каталог сценариев» поверх экрана 3.

**Завершение:** закрытие модалки или «Пропустить»/закрытие на любом экране → «Добро
пожаловать».

### 4.2. Модалка «Каталог сценариев» — `ScenarioCatalogModal`

Новый компонент на base-ui `Dialog`. Открывается поверх текущего экрана.

**Структура:** заголовок «Каталог сценариев» + [×]; поиск по названию; чипсы категорий
(мульти-селект); сетка карточек (название + одно предложение бизнес-цели, **без иконок**).

**Контекст `returnTo`:** `"onboarding" | "wizard-step-1" | "launcher"`.

**Поведение выбора сценария:**
- `onboarding` / `launcher` → сценарий «коммитится»: стартует флоу создания сигнала,
  визард открывается на **шаге 2** (пред-шаг сайта при необходимости отрабатывает
  `GuidedSignalSection`). Модалка закрывается.
- `wizard-step-1` → модалка закрывается, сценарий подсвечивается на шаге 1; если его там
  не было — добавляется первой карточкой списка.

**Поведение закрытия (без выбора):**
- `onboarding` → «Добро пожаловать».
- `wizard-step-1` → возврат на шаг 1.
- `launcher` → возврат на экран, с которого вызвали (НЕ всегда «Добро пожаловать»).

### 4.3. Шаг 1 визарда — переделка `Step1Scenario`

Заменяет текущие 6 карточек выбора типа сигнала.
- Секция **«Базовые сценарии»** — 6 карточек (`isBase`).
- Секция **«Подобрано для вас»** — 4 карточки (`isCurated`).
- Кнопка **«Все [N] сценариев»** → модалка каталога (`returnTo: "wizard-step-1"`).
- Карточка: название + одно предложение бизнес-цели, без иконок.
- Клик по карточке → выбор сценария → шаг 2 с предзаполнением.
- Сценарий, выбранный в каталоге и отсутствующий в секциях → добавляется первой карточкой
  и подсвечивается как выбранный.
- Поиска на шаге 1 **нет** — он живёт только в каталоге.
- Чат-бот **активен** (онбординг закончился): вопрос «что за сценарий, как работает»
  отвечается в стандартном промпт-баре снизу, не выбивая из шага. Отдельных окон/панелей
  сценария **нет**.

### 4.4. Экран «Добро пожаловать»

Структура трёх карточек шагов не меняется. На карточке «Создать сигнал» (шаг 1) между
описанием и кнопкой добавляется строка-мотиватор:

> **Под вашу компанию подобрано [N] сценариев**

Правка в `onboarding-step-cards.tsx`.

### 4.5. Боковой лаунчер

`LaunchFlyout`: в секцию «Новый сигнал» добавляется кнопка **«Все [N] сценариев →»** →
модалка каталога (`returnTo: "launcher"`). 6 шаблонов лаунчера переходят на единую
библиотеку сценариев (`scenarios.ts`, базовые сценарии) вместо локального `SIGNAL_TEMPLATES`.

### 4.6. Шаг 2 визарда

Предзаполняется на основе `signalType` выбранного сценария (существующая seeded-логика
предзаполнения интересов/триггеров). Все поля **редактируемые**. Дальше — текущий флоу
без изменений.

## 5. Блок 2 — экран запущенной кампании

### 5.1. Новый экран и вью

`View` += `{ kind: "campaign"; campaign: { id: string; name: string } }`.
Новый компонент `CampaignScreen` (`sections/campaigns/campaign-screen.tsx`) — вертикальная
лента.

### 5.2. Модель запуска

- Клик «Запустить» → экшен `campaign_launched`: кампании `status: "active"`,
  `launchedAt: now`; навигация на `view.kind: "campaign"`. **Мгновенно**, без промежуточного
  экрана ожидания.
- Клик по active-кампании в разделе «Кампании» → `campaign`.
- Клик по черновику/запланированной кампании → `workflow` (текущее поведение).

### 5.3. Структура экрана (4 блока)

1. **Шапка кампании** — название · тип · дата запуска · бюджет. Читаем поля `Campaign`;
   недостающие (напр. `budget`) добавляем в модель с разумным дефолтом.
2. **Workflow** — `WorkflowMiniPreview`: живая мини-отрисовка реального графа кампании,
   **не интерактивная** (масштаб + `pointer-events: none`), переиспользует существующий
   рендер графа. Кнопка «Открыть workflow».
3. **Провайдеры данных** — однострочные карточки: точка статуса · имя · текст статуса ·
   цифра сигналов/день.
4. **CTA «Перейти в статистику»** — пока статистики нет — `disabled`.

### 5.4. Провайдеры — этапы и анимация

Универсальные этапы: **Подключение → Премодерация → Подключён → генерация сигналов.**
«Подключён» — не конечный статус; конечный — «~N сигналов/день».

`src/data/providers.ts` — 4 провайдера, захардкожены, одинаковы для всех кампаний.
Цифры условные:

| Провайдер | Время выхода | Конечный статус            | Потенциал (в процессе)        |
|-----------|--------------|----------------------------|-------------------------------|
| Билайн    | 2 с          | Подключён · ~5 сигналов/день   | до 2 000 сигналов/день    |
| Мегафон   | 3 с          | Подключён · ~12 сигналов/день  | до 4 000 сигналов/день    |
| МТС       | 5 с          | Подключён · ~8 сигналов/день   | до 3 000 сигналов/день    |
| Tele2     | —            | застревает на ранней стадии    | до 5 000 сигналов/день    |

- Цифра объёма: подключённый → «~N сигналов/день» (факт); в процессе → «до N сигналов/день
  после подключения» (потенциал).
- **Анимация:** при маунте `CampaignScreen` статусы идут по таймеру. Меняется только текст
  статуса и точка (● подключён / ○ в процессе). Этапы: Подключение → Премодерация →
  Подключён · ~N сигналов/день. Tele2 остаётся на «Подключение» или «Премодерация».
- Таймеры — в `ref`, cleanup на unmount (паттерн AI-цикла из `workflow-view.tsx`).
  Анимация перезапускается при каждом открытии экрана — для демо приемлемо.

### 5.5. Workflow-экран

- Кнопка «Открыть workflow» → `view.kind: "workflow"`; на workflow-экране есть кнопка
  «назад» на экран кампании.
- **Read-only — только когда workflow открыт у запущенной кампании** (`launched: true` на
  workflow-вью): без правки нод, без кнопки «Запустить», только просмотр + «назад».
- У **незапущенной** кампании workflow-экран остаётся **редактируемым** (текущее поведение).
- Мини-превью на экране кампании использует тот же рендер графа.

**Зафиксировано:**

- Лаунчер — в объёме этой итерации (точка входа в каталог).

**Вне объёма (открытые вопросы ТЗ — следующие итерации):**

- Откуда берётся библиотека сценариев.

## Приложение A — Библиотека сценариев (черновик, 24 шт.)

Легенда: **Б** — базовый (`isBase`), **П** — подобрано для вас (`isCurated`).
`signalType` — тип сигнала под капотом.

### Базовые сценарии (6, `isBase: true`)

| Название | Категория | signalType | Описание (бизнес-цель) |
|----------|-----------|------------|------------------------|
| Регистрация | Онбординг | registration | Довести до конца брошенную регистрацию или оформление. |
| Первая сделка | Привлечение | first-deal | Подтолкнуть нового клиента к первой покупке. |
| Апсейл | Апсейл | upsell | Поднять чек активного клиента релевантным предложением. |
| Удержание | Удержание | retention | Удержать клиента, поймав ранние признаки оттока. |
| Возврат | Возврат | return | Вернуть клиента в оптимальный момент повторного контакта. |
| Реактивация | Реактивация | reactivation | Разбудить давно неактивного клиента. |

### Подобрано для вас (4, `isCurated: true`)

| Название | Категория | signalType | Описание |
|----------|-----------|------------|----------|
| Брошенная корзина | Привлечение | registration | Вернуть тех, кто не завершил оформление заказа. |
| Спящий клиент | Реактивация | reactivation | Реактивировать клиентов без активности 90+ дней. |
| Отток-сигнал | Удержание | retention | Поймать интерес к конкурентам до того, как клиент уйдёт. |
| Истёк продукт | Возврат | return | Предложить продление к дате окончания продукта. |

### Каталог — остальные 14 (`isBase: false`, `isCurated: false`)

| Название | Категория | signalType | Описание |
|----------|-----------|------------|----------|
| Рост чека | Апсейл | upsell | Апсейл по росту активности и среднего чека клиента. |
| Кросс-продажа | Апсейл | upsell | Предложить смежный продукт под текущую потребность. |
| Премиум-апгрейд | Апсейл | upsell | Перевести клиента на старший тариф или пакет. |
