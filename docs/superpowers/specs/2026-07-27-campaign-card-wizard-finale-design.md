# Карточка кампании как финал визарда

Дата: 27 июля 2026
Ветка: `feature/track-card`

## TL;DR

Карточка кампании становится финальным экраном визарда. Описание цепочки перестаёт быть сплошным текстом: значения параметров выносятся в кликабельные теги-пилюли, каждый из которых ведёт либо на шаг визарда, либо в редактор по месту. Пока кампания в черновике, любой параметр правится точечным визитом на свой шаг; после запуска теги остаются как носители значений, но клик снимается.

Три следствия, меняющие существующий код: визард получает сериализуемый снапшот на кампании, описание получает сегментную модель вместо строки, нодо-блоки с карточки снимаются как дубль тегов.

# 1. AS IS

## 1.1. Визард и карточка не связаны

`View` — плоский union (`src/state/app-state.ts:201`), ветка `guided-campaign` не несёт идентификатора кампании. Адреса «визард этой кампании» не существует.

`campaign_created_from_wizard` (`src/state/app-state.ts:523`) проецирует `StepData` в поля `Campaign` и сам `StepData` выбрасывает. Роутит уже на карточку (`view: { kind: "campaign" }`), так что «карточка как финал визарда» частично действует — нет только обратного пути.

`wizardSeed` (`src/state/app-state.ts:322`) — единственный механизм гидрации визарда извне, помечен dev/test-only и ставится только действием `__dev_seed__`.

## 1.2. Потери при проекции StepData → Campaign

На `Campaign` не переносятся: `intent`, `analysisMode`, `budgetMode`, `apiKey`, `ownSignalType`.

`intent` определяет состав шагов (`stepsForIntent`, `wizard-steps.ts:15`). Обратно из `sourceType` не выводится: `deriveSourceType` (`src/types/campaign.ts:15`) склеивает `signals` и `signals-comms` в один `new`.

`StepData.files` — сырые браузерные `File[]`; `Campaign.files` — `{ name, rowCount }[]`. Объекты `File` невосстановимы.

## 1.4. Смена шаблона существует, но не на карточке

`NodeTemplateSelect` (`node-template-select.tsx`) реализует выбор из шаблонов канала, превью каждого и пункт «Создать новый шаблон»; применяется через `workflow_node_field_set`. Смонтирован только в карточке узла графа (`node-card-content.tsx:495`). Триггер сверстан как строка сетки узла (`rowGrid`, `node-template-select.tsx:63`) и неотделим от содержимого.

## 1.5. Описание не держит inline-элементы

`describeWorkflow` (`src/state/graph-description.ts:248`) возвращает `DescriptionStage[]`, где `body` — сплошная строка, а коммуникации лежат отдельным массивом `messages`. `WorkflowDescription` (`workflow-description.tsx:44`) рендерит это как `<p>` и `<ul>`. Точки вставки элемента внутрь `body` нет — есть только `stageSlots`, вставляющий блок под этапом.

Значений, подлежащих тегированию, в тексте нет: число строк базы, перечисление триггеров, каналы, бюджет и режим анализа в формулировках отсутствуют. `describeWorkflow` — чистая функция от графа и библиотеки шаблонов, состояние кампании не читает; факты подаёт вызывающий (`DomainStatuses`, третий аргумент).

## 1.6. Каскад шагов

`computeStepTransition` (`wizard-navigation.ts:47`) обрабатывает два случая: смена сценария сбрасывает всё в `initialStepData`, смена цели сбрасывает всё кроме сценария. Для остальных шагов каскада нет — возврат на пройденный шаг прыгает на `maxStep`, ничего не пересчитывая.

Каталог интересов и триггеров зависит от направления бизнеса аккаунта (`resolveInterestsForDirection`), а не от сценария. То есть текущий сброс по сценарию стирает данные, которые от сценария не зависят.

Шаг «Бюджет» пересчитывается по массиву `[data.scenario, data.sourceType, data.channels, data.fileRowCount]` (`step-budget.tsx:164`) — исчерпывающий список влияющих на него значений.

## 1.7. Визард рендерит все пройденные шаги

`visibleSteps` — от 1 до `maxStep`, каждый шаг на полный экран в вертикальной скролл-колонке (`campaign-workspace.tsx`). Переход на шаг — скролл к позиции. «Назад» ведёт на предыдущий шаг колонки. Текст основной кнопки задан константой на каждом шаге (`StepFooter.continueLabel`, `step-footer.tsx:12`).

Шаг «Сценарий» — исключение: у него нет ни `StepFooter`, ни `onBack`; выбор сценария применяется сразу по клику (`step-1-scenario.tsx:107` вызывает `onNext` из обработчика).

## 1.8. Кэш графа без инвалидации

`workflow-graph-cache.ts` — module-scope `Map` без операции сброса. Карточка читает `getCachedGraph(campaign.id) ?? createTemplate(...)` (`campaign-screen.tsx:105`), то есть кэш всегда побеждает шаблон.

# 2. TO BE

## 2.1. Снапшот визарда на кампании

`StepData.files` переходит на лёгкую модель (см. 2.11), после чего `StepData` целиком сериализуем. Поэтому отдельного параллельного типа не заводим:

```ts
/** Сериализуемый слепок ответов визарда. Совпадает со StepData —
 *  после перевода files на BaseFile в нём нет несериализуемых значений. */
export type WizardSnapshot = StepData
```

`Campaign` получает поле `wizardData?: WizardSnapshot`.

Жизненный цикл:

1. Пишется при `campaign_created_from_wizard`.
2. Перезаписывается при коммите правки с шага визарда (см. 2.7).
3. Копируется при `campaign_duplicated` — дубль черновика должен оставаться правимым.
4. Удаляется при переводе кампании в `active`.

После удаления снапшота визард для этой кампании недоступен, и двух источников правды не остаётся.

**Снапшот нужен только для гидрации визарда.** Значения для тегов описания он не поставляет — см. 2.3. Это и делает возможным его удаление при запуске без потери значений в тексте.

## 2.2. Сегментная модель описания

`DescriptionStage.body` меняет тип со `string` на `DescriptionSegment[]`:

```ts
type DescriptionSegment =
  | { kind: "text"; text: string }
  | { kind: "tag"; tag: DescriptionTag }

interface DescriptionTag {
  id: string
  label: string
  target: TagTarget
  /** Раскрывается по наведению — остаток схлопнутого перечисления. */
  hoverList?: string[]
}

type TagTarget =
  | { kind: "wizard-step"; step: WizardStepId }
  | { kind: "template"; nodeId: string }
  | { kind: "node-fields"; nodeId: string }
  | { kind: "domains" }
```

Единственная цель, уводящая с карточки, — `wizard-step`. Остальные три раскрываются поповером у самой пилюли (см. 2.6).

Строки коммуникаций (`DescriptionStage.messages`) получают то же представление: название шаблона становится сегментом-тегом с целью `template`, несущей `nodeId` своей ноды.

`describeWorkflow` остаётся чистой функцией. Третий аргумент расширяется с `DomainStatuses` до `CampaignFacts`:

```ts
export interface CampaignFacts {
  /** Домены на модерации — существующее поведение DomainStatuses. */
  pending: string[]
  /** Все домены триггеров кампании со статусами — для поповера доменов. */
  domains?: { domain: string; status: DomainStatus }[]
  baseRows?: number
  triggers?: string[]
  channels?: Channel[]
  budget?: number
  /** «Разовый» / «потоковый». Отсутствует у собственной базы. */
  analysisMode?: AnalysisMode
  scenarioName?: string
  /** Шаги, доступные для правки. Пусто → теги без цели wizard-step. */
  editableSteps?: WizardStepId[]
}
```

Собирает эти факты `CampaignScreen`, где они уже доступны.

Тег с целью `wizard-step` строится **только** если его шаг есть в `editableSteps`. `CampaignScreen` наполняет `editableSteps` из `stepsForIntent(wizardData.intent)` и только для черновика; после запуска (снапшот удалён) список пуст, и все шаговые теги рендерятся как неинтерактивные носители значений. Это и есть механизм 2.12 — не отдельная ветка рендера, а пустой список целей.

## 2.3. Инвентарь тегов

| Тег | Значение откуда | Цель |
|---|---|---|
| база на N строк | `campaignBaseRows(campaign)` | шаг «Файл» |
| перечисление триггеров | `Campaign.triggers` | шаг «Интересы» |
| ещё N триггерам | остаток перечисления | шаг «Интересы» |
| каналы | `Campaign.channels` | шаг «Каналы» |
| бюджет | `Campaign.budget` | шаг «Бюджет» |
| разовый / потоковый | **выводится из `Campaign.sourceType`** | шаг «Режим» |
| сценарий | `Campaign.scenario` | шаг «Сценарий» |
| название шаблона | `describeMessage` | поповер выбора шаблона |
| пауза N дней | параметры узла `wait` | поповер правки задержки |
| домены | `triggerConfig.added` и `accountSettings.ownDomains` | поповер со статусами |

**Все значения берутся с `Campaign`, ни одно — со снапшота.** Ключевой случай — режим анализа: `sourceType === "stream"` ⇒ «потоковый», `"new"` ⇒ «разовый», `"own"` ⇒ тега нет вовсе (у собственной базы шага «Режим» не существует). Это ровно обратное преобразование к `deriveSourceType` для не-own веток, поэтому значение восстановимо и после удаления снапшота.

Перечисление триггеров: два названных, остаток в схлопку. Форма числительного — через `pluralRu`. Схлопка ведёт туда же, куда и названные триггеры; по наведению показывает список остатка (`hoverList`).

Тег не рендерится, когда значения нет: нет базы — нет тега базы, нет каналов — нет тега каналов. Текст вокруг тега при этом должен оставаться связным, поэтому фразы собираются вместе с тегом, а не обрамляют дыру.

## 2.4. Визуал тега

Пилюля в потоке текста: скруглённая рамка, иконка слева, значение внутри, выравнивание по базовой линии строки.

Два визуальных класса по типу цели:

- **Цель — шаг визарда.** Нейтральная рамка и фон карточки. Иконка берётся из новой карты `STEP_ICON`, парной существующей `STEP_LABELS` (`campaign-stepper.tsx:8`): сценарий `Route`, цель `Target`, интересы `Gauge`, режим `Repeat`, файл `Database`, каналы `MessageSquare`, бюджет `Wallet`, интеграция `Plug`.
- **Цель — узел графа, шаблон или настройки.** Рамка и цвет текста из `NODE_STYLES` соответствующего узла, иконка из `NODE_ICON` (`node-visuals.ts`). Этот модуль уже объявлен источником правды для тегов.

Жёлтый в тегах не используется: акцент остаётся редким сигналом (PRODUCT.md, принцип 2), а тегов на карточке до семи штук.

Тултип с задержкой 1 секунда, текст «Нажмите для изменения». Задержка задаётся через `TooltipProvider delay`. Неинтерактивный тег (после запуска) тултипа не несёт.

## 2.5. Вход в визард с карточки

Новое действие: `campaign_step_edit_requested { campaignId, step }`, где `step` — `WizardStepId`. Переводит `view` в:

```ts
| { kind: "guided-campaign";
    initialScenario?: { id: string; name: string };
    editing?: { campaignId: string; step: WizardStepId } }
```

`ViewAddress` получает парные поля **дополнительно** к существующим `scenarioId`/`scenarioName`, которые остаются нетронутыми:

```ts
| { kind: "guided-campaign"
    scenarioId?: string; scenarioName?: string
    campaignId?: string; step?: WizardStepId }
```

Возврат браузера тогда работает и для правки. Рехидрация адреса ищет кампанию по id; если её нет или снапшот удалён — падает на обычный `guided-campaign` без `editing`.

`GuidedCampaignSection` при наличии `editing` гидрирует `CampaignWorkspace` снапшотом кампании и открывает шаг изолированно. Гейт анкеты в режиме правки не применяется — кампания уже создана.

Изолированный режим: `visibleSteps` содержит только запрошенный шаг. Колонка дорастает по факту правки — как только правка обнуляет шаги ниже, они появляются под текущим.

Степпер в изолированном режиме показывает полный список шагов, но кликабельны только те, что попали в колонку. Прыгать на непройденные шаги правки нельзя — иначе точечный визит превращается в повторный проход визарда.

## 2.6. Клик по тегу вне визарда

Три цели раскрываются поповером, привязанным к позиции пилюли в строке. Карточка не покидается ни в одном из трёх случаев — единственная цель, уводящая с неё, это шаг визарда.

**Шаблон, цель `template`.** Содержимое поповера — существующий список из `NodeTemplateSelect`: шаблоны канала узла, «глаз» превью у каждого, разделитель, пункт «Создать новый шаблон».

- Выбор шаблона применяется к узлу через `workflow_node_field_set` по ключу params канала. Описание перерисовывается сразу: карточка уже подписана на версию кэша графа через `useCachedGraphVersion` (`campaign-screen.tsx:77`).
- Превью открывает `TemplatePreviewDrawer` и поповер не закрывает.
- «Создать новый шаблон» открывает дровер создания для канала узла и поповер закрывает.

Требует разделения `NodeTemplateSelect`: содержимое поповера выносится в отдельный компонент (`NodeTemplateList`), которым пользуются оба триггера — строка узла в графе и тег в описании. `NodeTemplateSelect` сохраняет текущий публичный API и внутри рендерит новый компонент, поэтому карточка узла графа не меняется.

**Пауза, цель `node-fields`.** Содержимое поповера — `WaitFields` (`wait-fields.tsx:51`) без изменений. Компонент самодостаточен: принимает идентификатор узла и параметры, диспатчит `workflow_node_field_set` сам, несёт свои поля режима и длительности. Описание перерисовывается тем же путём, что и после смены шаблона.

**Домены, цель `domains`.** Информационный поповер, правки в нём нет. Показывает все домены триггеров кампании со статусом каждого: «На проверке» с таймером модерации, «Одобрен», «Отклонён». Бейджи и подписи берутся из блока настроек (`DomainStatusBadge`, `domains-block.tsx:35`), для чего он экспортируется; формулировки статусов не должны разойтись между реестром и карточкой.

Поповер добавляет на карточку то, чего сегодня нет нигде в кампании: одобренные и отклонённые домены не показываются, хотя именно они определяют итоговый состав аудитории. Тег живёт внутри существующей фразы о модерации, поэтому условие вывода этой фразы не меняется — она появляется при наличии хотя бы одного домена на проверке.

Правка доменов остаётся в редакторе интересов и триггеров и адресуется тегом триггеров.

Правки через поповеры пишутся в durable-поля графа и в снапшот визарда не попадают: параметры узлов ответом визарда не являются.

## 2.7. Применение правки и текст кнопок

**Коммит ровно один — на основной кнопке последнего шага сессии правки.**

Спека не оговаривала промежуточные «Далее», а они возможны: каскад (2.8) может обнулить шаги ниже, и по ним придётся пройти. Если писать в кампанию на каждом «Далее», брошенная на полпути правка оставит черновик с новыми каналами и `budget: null` — незапускаемым. Поэтому «Далее» ведёт по обнулённым шагам **внутри изолированной сессии и ничего не пишет наружу**; вся правка уходит в кампанию, снапшот и граф одной транзакцией.

Футер изолированного режима:

| Позиция | Подпись | Действие |
|---|---|---|
| слева | Отмена | вернуться на карточку, ничего не применив |
| справа, в колонке не осталось непройденных обнулённых шагов | Применить и вернуться | коммит + возврат на карточку |
| справа, в колонке есть непройденные обнулённые шаги | Далее | перейти к следующему шагу сессии |

«Применить и вернуться» активна и когда значение не менялось — коммит тогда пустой, кнопка просто возвращает.

Требует живого определения изменения: `StepProps` расширяется коллбеком `onValueChange`, через который шаг непрерывно сообщает текущий выбор наверх. `CampaignWorkspace` сравнивает его со снапшотом и решает, что обнулилось. Сегодня сравнение происходит только в момент submit.

`StepFooter` получает `backLabel` (по умолчанию «Назад») и продолжает получать `continueLabel` — теперь вычисляемый, а не константный.

**Шаг «Сценарий» футера не получает.** Он сохраняет автоприменение: клик по сценарию поднимает диалог о пересборке графа (2.9), подтверждение коммитит правку, пересобирает граф и возвращает на карточку; отмена оставляет на шаге. Клик по уже выбранному сценарию диалога не поднимает — просто возвращает на карточку.

Коммит — одно действие `campaign_wizard_edit_applied { campaignId, stepData }`, которое проецирует `StepData` в поля `Campaign` тем же кодом, что и `campaign_created_from_wizard` (проекция выносится в общую функцию), и перезаписывает `wizardData`. Перестройка графа (2.9) выполняется в `GuidedCampaignSection` до диспатча, поскольку кэш графа живёт вне redux-состояния.

## 2.8. Каскад сброса

| Изменили | Обнуляется | Граф |
|---|---|---|
| Сценарий | бюджет | полная перестройка |
| Цель | состав шагов и всё ниже цели | полная перестройка |
| Режим анализа | бюджет | без изменений |
| База | бюджет | без изменений |
| Каналы | бюджет | мерж |
| Интересы и триггеры | ничего | без изменений |
| Бюджет | ничего | без изменений |

Обнулённый шаг сбрасывается в значение по умолчанию и проходится заново вручную. Автоматического пересчёта нет, в том числе для рекомендуемой суммы бюджета.

Сброс по сценарию сокращается: сегодня он стирает интересы, триггеры, базу и каналы, которые от сценария не зависят. Остаётся только бюджет.

Смена цели сохраняет текущее поведение полного сброса ниже — она меняет сам состав шагов, а не значения. Тега «цель» в описании нет, поэтому этот случай возникает только в обычном проходе визарда, не в правке.

Карта зависимостей выносится в `wizard-navigation.ts` отдельной таблицей `STEP_INVALIDATES: Partial<Record<WizardStepId, WizardStepId[]>>` — она обслуживает и обычный проход, и изолированную правку.

## 2.9. Перестройка графа

Кэш получает операцию сброса: `invalidateCachedGraph(campaignId)` в `workflow-graph-cache.ts` (с тем же `bumpVersion`, что и остальные записи).

**Смена каналов — мерж.** Новая чистая функция `mergeChannelNodes(graph, nextChannels, ...)` в `workflow-templates.ts`: удаляются коммуникационные узлы снятых каналов вместе с их рёбрами (входящие переподключаются на цель исходящего, чтобы цепочка не рвалась), добавляются узлы по умолчанию для новых каналов. Задержки, условия, разветвления и отредактированные тексты остальных узлов сохраняются. Кэш обновляется результатом мержа.

**Смена сценария — полная перестройка.** Граф собирается заново из `createTemplate` по новому типу сигнала, кэш сбрасывается. Ручные и ИИ-правки структуры теряются, поэтому перед применением показывается предупреждение с подтверждением.

## 2.10. Снятие нодо-блоков с карточки

`CampaignScenarioNodeBlock` и `CampaignCommunicationNodeBlock` с карточки снимаются: после тегирования они показывают то же, что несёт текст, и создают второй путь к той же правке. Цветовая привязка к графу переносится в теги (2.4).

`stageSlots` в `WorkflowDescription` для этапов «Старт» и «Первое касание» больше не используется. Сам механизм слотов остаётся.

Дровер интересов и триггеров снимается с карточки: правка идёт переходом на шаг. `ScoringRow` остаётся смонтирован только в карточке узла графа, ветка `view.kind === "campaign"` из него убирается (`node-card-content.tsx:188`). `openScoringDrawer` продолжает обслуживать граф.

Тег названия шаблона несёт полный список шаблонов канала, превью каждого и пункт «Создать новый шаблон». Это шире текущей возможности блока, который умеет только открыть редактор.

## 2.11. Шаг «Файл» на лёгкой модели

`StepData.files` меняет тип с `File[]` на `BaseFile[]`, где

```ts
export interface BaseFile { name: string; rowCount: number }
```

— тот же тип, что несёт `Campaign.files`.

`simulateRowCount` вызывается в момент получения файла, дальше по системе идёт лёгкий объект. `DropZone` получает `File` только внутри обработчика загрузки и наружу отдаёт уже `BaseFile`.

Сравнение «набор не изменился» переходит с равенства по ссылке (`step-file.tsx:120`) на сравнение по имени и числу строк. Хеширование запускается только для реально нового файла.

Распределение суммарного числа строк по файлам в `campaign_created_from_wizard` (`app-state.ts:527–537`) удаляется: число строк известно по каждому файлу отдельно. `fileRowCount` остаётся как сумма — его читает шаг «Бюджет».

## 2.12. Поведение после запуска

Теги рендерятся как пилюли и продолжают показывать значения — они носители данных, а не только аффорданс. Клик и тултип снимаются. Механизм — пустой `editableSteps` в `CampaignFacts` (2.2), а не отдельная ветка рендера. Это повторяет существующую логику `readOnly` в `NodeTemplateSelect`, где значение остаётся, а попап уходит.

Поповерные теги (шаблон, пауза) после запуска тоже теряют клик; тег доменов остаётся информационным и кликабельным — он ничего не правит.

Визард для запущенной кампании недоступен, снапшот удалён.

# 5. Риски

**Смена типа `DescriptionStage.body`** ломает `graph-description.test.ts` и `workflow-description.test.tsx` целиком — оба переписываются на сегменты. Это самая широкая по diff-у часть трека, делать её первой.

**`mergeChannelNodes`** — единственная существенно новая логика. Риск порвать граф на снятии канала из середины цепочки. Покрывается юнит-тестами на чистой функции до подключения к UI.

**`@visual`-базлайны** карточки кампании и визарда изменятся. Перегенерировать в конце трека, направив playwright на порт worktree, иначе снимется main-чекаут.

**`campaign-cost-parity.test.ts`** проверяет совпадение сумм карточки и экрана оплаты. Любая правка, трогающая граф, обязана его сохранять — критерий 20.

# 6. Критерии приёмки

1. Кампания в черновике: клик по тегу базы открывает шаг «Файл» изолированно, уже загруженные файлы показаны с именем и числом строк, перезагрузка не требуется.
2. Клик по тегу триггеров открывает шаг «Интересы»; основная кнопка сразу читается как «Применить и вернуться».
3. Правка интересов и триггеров с возвратом на карточку не обнуляет бюджет и не перестраивает граф.
4. Снятие канала на шаге «Каналы» обнуляет бюджет, шаг «Бюджет» появляется в колонке, основная кнопка меняется на «Далее».
5. Тот же шаг «Каналы», открытый и закрытый без изменений, оставляет кнопку «Применить и вернуться» и бюджет нетронутым.
6. «Отмена» на шаге правки возвращает на карточку, не изменив ни кампанию, ни граф, ни снапшот.
7. Уход с шага «Каналы» по «Отмене» после снятия канала, но до прохода бюджета, оставляет кампанию с прежними каналами и прежним бюджетом.
8. Смена каналов сохраняет отредактированные вручную тексты остальных узлов графа и убирает узлы снятого канала.
9. Смена сценария показывает предупреждение; после подтверждения граф собран из нового шаблона, ручные правки отсутствуют, возврат на карточку происходит сразу.
10. Клик по тегу названия шаблона открывает поповер у самой пилюли со списком шаблонов канала и пунктом «Создать новый шаблон».
11. Выбор другого шаблона в поповере перерисовывает описание без перезагрузки карточки; превью открывается, не закрывая поповер.
12. Клик по тегу паузы открывает поповер с полями режима и длительности; правка перерисовывает описание.
13. Клик по тегу доменов открывает поповер со всеми доменами триггеров кампании и статусом каждого, включая одобренные и отклонённые.
14. Ни один тег, кроме ведущих на шаг визарда, не уводит с карточки кампании.
15. Число строк базы, перечисление триггеров, каналы, бюджет, режим анализа и сценарий присутствуют в тексте описания как теги.
16. Перечисление триггеров показывает два названия и схлопку с корректной формой числительного; наведение на схлопку показывает остаток.
17. Наведение на любой тег через секунду показывает «Нажмите для изменения».
18. Описание перезаписывается после каждой применённой правки без перезагрузки карточки.
19. Нодо-блоки «Старта» и «Первого касания» на карточке отсутствуют.
20. Дровер интересов и триггеров с карточки не открывается; в карточке узла графа продолжает работать.
21. После запуска кампании теги показывают значения, клик и тултип не срабатывают, визард недоступен; тег режима анализа продолжает показывать «разовый»/«потоковый».
22. Дубль черновика открывается в визарде и правится так же, как оригинал.
23. Число касаний и суммы в блоке «Запуск» совпадают с экраном оплаты после любой правки, затронувшей граф.
