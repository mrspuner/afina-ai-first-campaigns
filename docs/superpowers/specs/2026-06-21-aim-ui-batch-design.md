# Design: батч UI-правок из aim (2026-06-21)

**Дата:** 2026-06-21
**Статус:** утверждён; авто-исполнение (план + реализация без отдельного подтверждения по решению пользователя).
**Ветка:** `feature/finish-campaign-first` (продолжаем поверх campaign-first работы; ещё не смержена).
**Источник:** очередь правок aim → `docs/edits/2026-06-21-aim.md` (15 правок).

## 0. Контекст

15 UI-правок, накиданных через aim на работающем прототипе (онбординг → визард кампании → оплата). Группируются в 6 тем. Часть (#5) осознанно разворачивает упрощёнку campaign-first (4-шаговый визард → динамический степпер по типу источника). Среда: имя папки репозитория содержит неразрывный пробел — работать через shell (`cd /tmp/afina-wt`) или ASCII-симлинк `/tmp/afina-wt/...` для Read/Write/Edit.

**Принципы:** прототип для валидации UX; переиспользуем существующие компоненты/паттерны; жёлтый — редкий сигнал; кириллица first-class.

## 1. Решения брейншторма (зафиксированы)

- **#5 гейтинг источника:** отдельные шаги визарда (степпер растёт), матрица в §C.
- **#10/#15 пересчёт бюджета:** пропорциональное масштабирование разбивки к своей сумме.
- **#1 поле сайта:** опциональное, отдельное, хранится в `companyWebsite` (разводим legacy-алиас).
- **Интересы:** для `new` и `stream` (не для `own`).
- **stream:** Интересы + Интеграция (API-ключ).

## A. Анкета — поле «Сайт компании» (#1)

**Файлы:** `src/sections/survey/survey-form.tsx`, `src/state/survey-validation.ts`, `src/types/survey.ts` (если нужно), `src/state/app-state.ts` (`survey_completed`/`survey_updated`).

Сейчас `SurveyForm` рендерит только textarea «Ваша задача» и пишет один и тот же текст в `taskDescription` И `companyWebsite` (legacy-алиас, который читает reducer для хаб-совместимости).

**Меняем:**
- Добавляем второй **опциональный** `Input` «Сайт компании» над/под задачей. Хранится в `survey.companyWebsite`.
- «Ваша задача» → только `survey.taskDescription`. Разводим алиас: на сабмите `companyWebsite = siteValue.trim()` (может быть пусто), `taskDescription = taskValue.trim()`.
- Валидация обязательности — **только на задаче** (`isTaskDescriptionValid`, ≥3 символа). Сайт можно пропустить.
- Reducer `survey_completed`: `accountSettings.companyWebsite` берётся из `action.survey.companyWebsite` (как сейчас), но теперь это реальный сайт, не дубль задачи. Если сайт пуст — не затирать существующий `accountSettings.companyWebsite` (текущий фоллбэк `|| state.accountSettings.companyWebsite` это уже обеспечивает).

**Тесты:** сабмит с пустым сайтом проходит (валиден); `companyWebsite`/`taskDescription` пишутся раздельно.

## B. Каталог сценариев / Шаг 1 (#2, #3, #4)

**Файлы:** `src/sections/campaigns/wizard/steps/step-1-scenario.tsx`, `src/sections/signals/scenario-card.tsx`, `src/data/scenarios.ts` (`curatedScenarioCount`, `SCENARIO_CATEGORIES`).

### #4 — реструктуризация (главное)
Сейчас шаг 1: чипы-фильтры + скролл-контейнер, сценарии сгруппированы по категориям, каждая категория свёрнута до `COLLAPSED_PER_GROUP = 3` с кнопкой «Показать ещё/Свернуть».

**Становится двухрежимным:**
1. **Дефолт — «Подобрали для вас»:** один блок с курируемыми сценариями (`SCENARIOS.filter(s => s.isCurated)`, N = `curatedScenarioCount`) карточками в сетке. Заголовок «Подобрали для вас». Под ним кнопка **«Показать все»**.
2. **Раскрытый (после «Показать все»):** полный каталог — существующие **чипы-фильтры категорий** + каждая категория показывает **ВСЕ** свои карточки (убираем `COLLAPSED_PER_GROUP`, «Показать ещё», «Свернуть»). Поиск остаётся. Состояние раскрытия — локальный `useState` (`showAll`), сбрасывается при входе на шаг.

Выбор карточки в любом режиме → `onNext({ scenario: id })` (авто-переход на следующий шаг), как сейчас.

### #3 — убрать внутренний скролл
Удаляем `max-h-[420px] overflow-y-auto pr-2 [scrollbar-*]` и связанные fade-градиенты (`canScrollUp`/`canScrollDown` и их вычисление). Контейнер растёт по высоте контента; вертикальный скролл — внешний (страница), как у остальных шагов.

### #2 — source-чип внутрь карточки
`SourceTypeChip` сейчас рендерится **под** карточкой (в обёртке `flex flex-col gap-1.5`) с текстом «Источник: {label}».
**Меняем:** маленький тег **внутри** `ScenarioCard` (угол/под описанием), текст — только label («Новая база» / «Поток» / «Своя база»), без слова «Источник:». Стиль — компактный badge, нейтральный (не жёлтый). Обёртку с внешним чипом убираем; чип становится частью `ScenarioCard` (новый опциональный проп `sourceLabel?: string`). `recommendedSourceType` → label через существующий `sourceTypeLabel()`.

## C. Шаг «Источник» — гейтинг + интеграция (#5, #6)

**Файлы:** `src/sections/campaigns/wizard/steps/step-source.tsx`, `step-2-interests.tsx`, `step-4-upload.tsx` (переиспользуем/адаптируем), новый `step-integration.tsx`, `campaign-workspace.tsx`, `src/sections/campaigns/wizard/wizard-navigation.ts`, `campaign-stepper.tsx`.

### #5 — динамический степпер по источнику
Шаг «Источник» = **только выбор источника** (3 radio-карточки). Интересы / Файл / Интеграция выезжают **отдельными шагами** после выбора. Матрица:

| Источник | Последовательность шагов |
|---|---|
| **new** | Сценарий → Источник → **Интересы** → **Файл (обязательно)** → Каналы → Бюджет |
| **own** | Сценарий → Источник → **Файл сигналов** → Каналы → Бюджет |
| **stream** | Сценарий → Источник → **Интересы** → **Интеграция (API-ключ)** → Каналы → Бюджет |

- **Интересы** — переиспользуем чип-логику из текущего `step-source.tsx` (`resolveInterests`/`resolveVertical`) или существующий `step-2-interests.tsx`. Для `new` и `stream`. Не для `own`.
- **Файл** для `new` — **обязательно** (нельзя продолжить без файла). Хедер «Загрузите вашу базу».
- **Файл сигналов** для `own` — обязательно, но семантика/копи как старая загрузка своих сигналов из раздела «Сигналы» (было `upload-signal-dialog.tsx`): «Загрузите ваш список сигналов» (готовая база сигналов, без скоринга), не «база аудитории». Используем `DropZone` + хеширование + `simulateRowCount`.
- **Каналы**, **Бюджет** — общие, в конце для всех.

**Динамика степпера:**
- Список шагов вычисляется из `stepData.sourceType` функцией `stepsForSource(sourceType)` → массив идентификаторов шагов. До выбора источника известны только Сценарий+Источник.
- `campaign-stepper.tsx` (`STEPPER_ITEMS`) и `campaign-workspace.tsx` (`renderStepContent`, `computeStepTransition`) переводятся на этот динамический список вместо хардкодных 4 шагов.
- Смена источника на шаге «Источник» пересобирает хвост шагов и сбрасывает downstream-данные (как `computeStepTransition` уже делает при смене сценария).
- `onBack`/`onNext` работают по индексу в динамическом списке.

### #6 — stream Интеграция (API-ключ)
Новый шаг `step-integration.tsx` (только для `stream`): инструкция по интеграции (короткий текст) + `Input` «API-ключ» (placeholder, заглушка). Значение пишем в `StepData` (новое опциональное поле `apiKey?: string`) — для прототипа не валидируем строго (непустой желательно, но не блокируем; решаем в плане). Заменяет старую плашку «Источник подключается автоматически» (она удаляется из `step-source.tsx` вместе с file-блоком — файл/интересы/интеграция теперь отдельные шаги).

## D. Шаг «Бюджет» — копи + пересчёт (#7, #8, #9, #10, #11)

**Файлы:** `src/sections/campaigns/wizard/steps/step-budget.tsx`, `src/sections/campaigns/campaign-budget-estimate.ts`, новый общий хелпер `src/sections/campaigns/scale-breakdown.ts`.

- **#7 «~»:** оценочные числа в разбивке (Сигналы/Коммуникация/Итого) показываем с префиксом `~` (формат `~₽ 117 000`). Это оценки.
- **#8 «~N контактов»:** в строке «Сигналы» перед суммой выводим `~N контактов`, где N = оценка размера базы (`baseSize = fileRowCount ?? FALLBACK_BASE`). Формат строки: `Сигналы · ~N контактов … ~₽ X`.
- **#9 подзаголовок:** «Рассчитали стоимость по выбранному источнику, каналам **и размеру базы**.» — хвост «и размеру базы» добавляем **только если** `data.fileRowCount` задан (база загружена); иначе текущий текст без хвоста.
- **#11 дневной бюджет:** для stream показываем `~₽ {dailyBudget}/день × {STREAM_DAYS} дн · потолок ~₽ {total}` (явно количество дней; `STREAM_DAYS = 30`).
- **#10 пересчёт при своей сумме:** при выборе «Своя сумма» разбивка пересчитывается **пропорционально**: своя сумма = «Итого»; Сигналы и Коммуникация масштабируются по их долям рекомендуемой разбивки (`scaleBreakdown(recommended, customTotal)`), `~N контактов` и любой прогноз касаний следуют за масштабом. При «Рекомендуемой» — исходная оценка. Хелпер `scaleBreakdown(breakdown, customTotal, recommendedTotal)` чистый и тестируемый: каждую строку × `(customTotal / recommendedTotal)`, последняя строка (Итого) = `customTotal` (чтобы избежать ошибок округления).

## E. Workflow-баг — наезд ноды «Скоринг» (#12)

**Файл:** `src/state/workflow-templates.ts` (`withScoring`).

Сейчас `withScoring` ставит ноду скоринга на `x = entry.x + STEP/2` (= 105) и сдвигает downstream на `STEP/2`. Ширина ноды ≥ `minWidth: 110` → «Скоринг» (x=105) наезжает на «Сигнал»/source (x=0).

**Фикс:** ставить скоринг на **полный STEP** (`entry.x + STEP`, = 210) и сдвигать downstream-ноды на **полный STEP** (210). Результат: источник(0) → скоринг(210) → первая(420) → … — ровный шаг 210, без наезда. Рёбра (`entry→scoring`, `scoring→first`) не меняются. Применяется к `new`/`stream` (как сейчас); `own` скоринг не получает.

**Тест:** после `withScoring` x-координаты соседних нод различаются ≥ STEP; нет двух нод ближе STEP/2.

## F. Экран оплаты (#13, #14, #15)

**Файлы:** `src/sections/campaigns/campaign-payment-screen.tsx`, общий `scale-breakdown.ts` (из §D).

- **#13 убрать блок:** удаляем amber-блок «Стоимость / Баланс / Не хватает» (`campaign-payment-screen.tsx:401-428`).
- **#14 инлайн-подсказка нехватки:** вместо удалённого блока — компактная инлайн-подсказка **«Не хватает ₽N»** рядом с выбором суммы, показывается **только если** `shortfall > 0` (`computeShortfall(balance, activeBudget) > 0`). Хватает → ничего не показываем. Работает и для «Рекомендуемой», и для «Своей суммы» (реагирует на `activeBudget`).
- **#15 пересчёт «Из чего складывается»:** при «Своей сумме» блок «Из чего складывается стоимость» (`cost.lines`) пересчитывается **пропорционально** своей сумме тем же `scaleBreakdown` (graph-based путь оплаты: масштабируем `cost.lines`/`paymentSplit` к `customValue` по доле от `cost.total`). При «Рекомендуемой» — исходный расчёт.

## Реализация — заметки

- **Два пути разбивки бюджета:** визард (`estimateCampaignBudget`) и оплата (`computeCampaignCost`+`splitCampaignPayments`) считают независимо. Пропорциональный пересчёт (#10/#15) применяем в каждом через общий чистый хелпер `scaleBreakdown`.
- **Динамический степпер (#5)** — самая крупная часть; изолировать в `stepsForSource()` + переключить `campaign-workspace`/`campaign-stepper`/`wizard-navigation` на него. Существующие `step-2-interests.tsx`/`step-4-upload.tsx` переиспользовать.
- **Границы:** не трогаем логику скоринга/артефактов/реестр подсказок сверх перечисленного. `own` = «файл сигналов» только по копи/семантике загрузки; пер-источниковая логика артефактов (§campaign-first) не меняется.

- Точный визуальный размер/позиция source-тега в `ScenarioCard` (#2) — по месту, по существующим badge-паттернам.
