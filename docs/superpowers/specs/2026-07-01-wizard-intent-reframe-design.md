# Рефрейм визарда на намерение + артефакты потоковых кампаний

**Дата:** 2026-07-01
**Статус:** утверждён к реализации
**Область:** `src/sections/campaigns/wizard/**`, `src/sections/artifacts/**`,
`src/sections/campaigns/campaign-screen.tsx`, `src/state/app-state.ts`

Документ из двух частей: **Часть I** — рефрейм визарда (§1–11), **Часть II** —
артефакты (файлы сигналов) потоковых кампаний (§12–19). Часть II опирается на
`analysisMode` из Части I; реализуются фазами (сначала I, потом II).

## Часть I. Рефрейм визарда

## 1. Задача

Переработать визард создания кампании так, чтобы **шаг 2** задавал вопрос по
**намерению пользователя** («Что хотите получить?»), а не по источнику данных
(«Откуда берём аудиторию?»). Ветвление, которое сейчас зашито в выбор источника
(`new / stream / own`), переформулируется в три пути по цели. Дополнительно
выделяется новый шаг **«Режим анализа»** (разовый / потоковый), а загрузка файла
становится явной во всех путях.

Проект — прототип для юзертестов (см. `PRODUCT.md`): цель правок — валидировать
UX ментальной модели «что я хочу получить», не перформанс.

## 2. Как сейчас (as-is)

Порядок шагов задаёт `stepsForSource(sourceType)` в
`src/sections/campaigns/wizard/wizard-steps.ts`, ключ ветвления — поле
`stepData.sourceType` (`"new" | "stream" | "own"`, `src/types/campaign.ts:3`).

| Источник | Цепочка шагов |
|----------|---------------|
| `new` (Новая база) | scenario → source → interests → file → channels → budget |
| `stream` (Поток) | scenario → source → interests → file → channels → budget |
| `own` (Свои сигналы) | scenario → source → file → channels → budget |

Ключевые факты:

- **Шаг 1** — `Step1Scenario` (выбор сценария), `SCENARIO_STEP = 1`.
- **Шаг 2** — `StepSource` (`steps/step-source.tsx`), заголовок *«Откуда берём
  аудиторию?»*, три радио-карточки `SOURCE_OPTIONS`, `SOURCE_STEP = 2`.
- **Разовый/потоковый** нигде не выделены как шаг — это зашито в `new` vs
  `stream`.
- **Коммуникация вкл/выкл** решается не на шаге 2, а внизу на шаге `channels`
  (`steps/step-channels.tsx`): опция *«Получить только сигналы»* (`noComms`,
  строки 92-115) даёт «вырожденную» кампанию с `channels: []`.
- Навигация и сброс данных — `computeStepTransition`
  (`wizard-navigation.ts`) + `handleNext` (`campaign-workspace.tsx:99`).
  Смена сценария → перемотка на `SCENARIO_STEP+1` + полный reset. Смена
  источника → перемотка на `SOURCE_STEP+1` + reset (с сохранением сценария).
- `integration`-шаг существует как компонент, но **не входит** в дефолтную
  цепочку (поток тоже грузит файл-базу).

## 3. Как должно быть (to-be)

Шаг 1 «Сценарий» **без изменений**. Шаг 2 становится развилкой по намерению с
тремя ответами. Пути:

| Путь | Ответ на шаге 2 | Цепочка шагов (после scenario → шаг 2) |
|------|-----------------|------------------------------------------|
| **A** | Только сигналы | interests → **analysis** → file → budget |
| **B** | Сигналы + коммуникация | interests → **analysis** → file → channels → budget |
| **C** | Коммуникация по своим сигналам | file → channels → budget |

Правила:

- **A (только сигналы)** — до `channels` не доходит (коммуникации нет по
  определению). Заканчивается бюджетом (только стоимость сигналов).
- **B (сигналы + коммуникация)** — полный путь, `channels` **обязателен** (≥1
  канал).
- **C (свои сигналы)** — своя база, без `interests` и без `analysis`; `channels`
  **обязателен**. По смыслу ≈ текущий `own`.
- **`analysis` (Режим анализа)** — новый шаг, только в A и B, между `interests`
  и `file`. Это флаг **разовый / потоковый**. Оба режима работают по одному и
  тому же загруженному файлу — **интеграция/API не нужны**, ветвления после
  этого шага нет.

## 4. Изменения вординга

- Шаг 2 заголовок: «Откуда берём аудиторию?» → **«Что хотите получить?»**.
- Варианты (namewording — «сигналы», не «сегмент»), голос «магия под капотом»:
  - **A · «Только сигналы»** — «Соберём горячую аудиторию по интент-сигналам.»
  - **B · «Сигналы + коммуникация»** — «Соберём аудиторию и запустим по ней рекламу.»
  - **C · «Коммуникация по своим сигналам»** — «Загрузите свою базу — запустим по ней коммуникацию.»
- Новый шаг `analysis` заголовок (черновой): «Разовый или потоковый анализ?»
  - «Разовый» — «Проверим базу один раз и соберём аудиторию.»
  - «Потоковый» — «Будем постоянно отслеживать новые сигналы.»

Итоговый копирайтинг можно докрутить при реализации — это прототип.

## 5. Модель данных

Заменяем одно поле-ключ ветвления двумя ортогональными полями в `StepData`
(`src/types/campaign.ts`):

- `intent: CampaignIntent` — `"signals" | "signals-comms" | "comms-own"` (A/B/C).
  Основной ключ ветвления вместо `sourceType`.
- `analysisMode: "once" | "stream"` — разовый / потоковый. Значим только для
  A и B; для C игнорируется.

`sourceType` (`"new" | "stream" | "own"`) читают downstream-шаги
(`step-file` — копия текста, `step-budget` — «сигналы бесплатно» для своих). Чтобы
не переписывать эти чтения, `sourceType` **выводится** из `(intent, analysisMode)`
чистой функцией-хелпером:

- `intent === "comms-own"` → `"own"`
- иначе `analysisMode === "stream"` → `"stream"`, `"once"` → `"new"`

(Реализационный выбор — держать `sourceType` производным ИЛИ мигрировать чтения на
`intent`/`analysisMode` — оставляется плану; рекомендация: производный хелпер,
минимальный дифф.)

Дефолты в `initialStepData`: `intent: "signals-comms"` (путь B — самый полный),
`analysisMode: "once"`.

## 7. Навигация и сброс данных

Поведение сохраняется 1:1 с текущим, ключ ветвления — `intent`:

- Смена сценария (шаг 1) → перемотка на шаг 2 + полный reset (как сейчас).
- Смена намерения (шаг 2) → перемотка на шаг 3 + reset downstream, сценарий и
  новый `intent` сохраняются (было «смена источника»).
- Возврат на пройденный шаг без смены ветки → прыжок на `maxStep`, данные
  сохранены.
- Смена `analysisMode` внутри пути A/B **не** меняет набор шагов (обе цепочки
  идентичны), поэтому спец-reset не нужен — обычное продвижение.

## 8. Бюджет для пути A

Путь A завершается `budget` без каналов. Шаг `budget` уже умеет пустой
`channels` (текущая ветка «без коммуникации» даёт `channels: []`), считая только
стоимость сигналов — переиспользуем это, отдельной логики не требуется.

## 9. Обратная совместимость снапшотов

`StepData` сохраняется в `LaunchRequest.stepData` для «Открыть и редактировать».
Старые снапшоты с `sourceType` и без `intent`: для прототипа допустимо не
мигрировать (свежие созданные кампании используют новую модель). Если понадобится
— вывести `intent` из старых `(sourceType, channels)` при гидрации. В план внести
как низкоприоритетный пункт.

## 10. Вне области (non-goals)

- Не трогаем шаг 1 «Сценарий».
- Не добавляем шаг «Интеграция/API» (поток работает по файлу).
- Не меняем логику расчёта стоимости и содержимое `interests`/`budget` кроме
  описанного.
- Не занимаемся общим рефакторингом визарда вне ветвления.

## 11. Открытые вопросы

Нет — все закрыты в ходе брейншторма:

- `?¹` файл при потоковом режиме → файл везде одинаковый, интеграции нет.
- `?²` «Получить только сигналы» на «Каналах» → убрать; каналы обязательны в B/C,
  «только сигналы» = путь A.

## Часть II. Артефакты потоковых кампаний (файлы сигналов)

## 12. Задача

Потоковые кампании непрерывно собирают сигналы — их надо отдавать как
скачиваемые файлы-артефакты: **дневные выжимки** + **общий файл** за весь период.
Разовый режим отдаёт один файл. Все файлы попадают в глобальный раздел
«Артефакты» **и** в секцию «Артефакты» карточки кампании, с кнопкой «Скачать».

## 13. Что генерится (правила)

Ключ — `analysisMode` (Часть I); в карточке после запуска выводится из кампании
(`sourceType`/поток).

- **Разовый** (`analysisMode="once"`, пути A и B; а также путь C) — **один**
  артефакт-файл (выжимка списка сигналов). Путь A → `kind: "signals"`, путь B →
  `"signals_conversions"` (как сейчас), путь C → как сейчас.
- **Потоковый** (`analysisMode="stream"`, пути A и B — **и с коммуникацией, и без**):
  - **дневные выжимки** — по файлу на «день», список сигналов за день;
  - **общий файл** — весь накопленный список сигналов за период; `count` = сумма
    дневных.
- **Путь C** (свои сигналы) — потока нет, дневных выжимок не производит.

## 14. Модель данных (`Artifact`)

Расширяем `Artifact` (`src/state/app-state.ts`):

- `variant: "single" | "daily" | "cumulative"` — роль файла в коллекции
  (по умолчанию `"single"` для существующих артефактов).
- `periodDate?: string` — для `daily`: покрываемый день (ISO-дата).
- `kind` остаётся (`"signals" | "signals_conversions"`).

Коллекция потока = все артефакты одной кампании: один `cumulative` + N `daily`.
Группировка в UI — по `campaignId`. Признак «потоковая коллекция» выводится из
кампании (`analysisMode`/`sourceType === "stream"`).

## 15. Генерация: ускоренный таймер

«Раз в день» имитируем **ускоренным таймером** (по образцу
`SCORING_WINDOW_MS = 8000`):

- Пока потоковая кампания `active`, каждые ~N сек (напр. 7 с) — новый `daily`
  через reducer-экшен (напр. `stream_digest_emitted`): seeded `count`,
  синтетическая дата = `launchedAt` + счётчик дней. Одновременно апдейт
  `cumulative` (`count += daily.count`; создаётся при первом дне).
- Счётчики сидируются детерминированно (как `providerSignalsPerDay` в
  `campaign-progress.tsx`).
- Останавливается на `paused`/`completed`. Мягкий предел (напр. 14 выжимок), чтобы
  список не рос бесконечно.

## 16. Скачивание (реальный CSV)

Заменяем текущие мок-`alert` (`signals-tab.tsx:65`, `artifact-screen.tsx:135`) на
реальную генерацию CSV по существующему Blob-паттерну
(`statistics-view.tsx:387`):

- helper `buildSignalsCsv(rows)` — seeded мок-строки (колонки: Телефон/хэш, Тип
  сигнала из `SIGNAL_TYPES`, Дата).
- Дневная = список за день; общий = конкатенация всех дней; single = один список.
- Кнопки «Скачать»: карточка списка, строки дневных выжимок, «Скачать общий»,
  секция карточки кампании.

### 17.2 Детальный экран коллекции

Переиспользуем `EntityCardShell` (как `artifact-screen.tsx`):

- назад «К артефактам», заголовок «Поток · <кампания>», мета «Поток активен ·
  обновлено …», действия «Скачать общий» + меню;
- секция **«Всего сигналов за период»** — крупное число (`text-brand`) + подпись;
- секция **«Дневные выжимки»** — список файлов по дням (каждый со «Скачать»),
  свежий — «формируется…», «Показать ещё»;
- секция **«Кампания-источник»** — сводка (сценарий, режим анализа, коммуникация,
  период).

Навигация: новый view (напр. `collection` по `campaignId`) **или** открытие
`cumulative`-артефакта как якоря коллекции — выбор оставлен плану. Разовый артефакт
открывается в тот же экран без секции «Дневные выжимки» (одно число + «Скачать»).

### 17.3 Секция «Артефакты» карточки кампании

`CampaignArtifactsBlock` / `campaign-screen.tsx`:

- потоковая кампания — компактная коллекция: строка «общий файл» + несколько свежих
  выжимок (или «N выжимок») со «Скачать» и ссылкой в детальный экран коллекции;
- разовая — один артефакт (как сейчас).

## 19. Порядок реализации

Две фазы: сначала **Часть I** (визард), затем **Часть II** (артефакты) — Часть II
опирается на `analysisMode` из Части I. `writing-plans` может развести на два плана.
