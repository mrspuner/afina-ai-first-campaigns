## Цель

Поверх модели `root + subdomains` (спека 3) дать пользователю добавлять свои домены и видеть их **судьбу**: новый неизвестный домен уходит на модерацию (pending, жёлто-оранжевый чип с часами), по таймеру часть одобряется/часть отклоняется; реестр в настройках — единая точка правды по статусам; описание сценария на этапе скоринга дописывает строку о судьбе pending-доменов.

## Решение о единственном источнике статуса (разрешение противоречия B2.6 ↔ B2.8)

B2.6 говорит «кампания лишь отражает статус», B2.8 — «домены со статусом durable на кампании». Чтобы статус не разъехался на таймере в двух местах:

- **Единый источник статуса — реестр аккаунт-уровня** (в `AccountSettings`): по каждому добавленному домену — `status: pending|approved|rejected` (+ время добавления для таймера).
- **`Campaign.triggerConfig`** (из спеки 3) хранит только **ссылку**: какой домен добавлен к какому триггеру. Статус **не дублирует** — читает из реестра при рендере.
- Таймер модерации живёт на реестре (аккаунт-уровень), идёт независимо от кампаний. Кампания отражает текущий статус.

## TO BE

### 1. Статусы домена (B2.2)

Чипы в раскрытой карточке триггера / панели:
- **системный активный** — нейтральный, ✕ исключает (как сейчас);
- **системный исключённый** — перечёркнутый, ↩ вернуть (как сейчас);
- **свой активный** (домен из известного списка / ранее одобренный) — зелёный (как сейчас);
- **свой на модерации (pending)** — жёлто-оранжевый чип с иконкой часов, **без текстовой подписи**.

Статуса **rejected в карточке триггера нет**: отклонённые домены просто удаляются из кампании. Все три статуса (pending/approved/rejected) видны только в реестре (B2.5).

### 2. Добавление своего домена — комбобокс (B2.4)

Кнопка «Добавить свой домен» открывает **комбобокс** (вместо текстового флоу через бар):
- выбрать **ранее занесённый** домен (из реестра) → подставляется сразу **активным обычным чипом**, модерация не требуется (статус в реестре уже approved/pending → отражается);
- либо **создать новый**:
  - если домен есть в `knownTriggerDomains` (системный список) → сразу активен (зелёный);
  - иначе → появляется чипом **pending** (жёлто-оранжевый, часы) и уходит в реестр на модерацию.

### 3. Реестр «Собственные домены и исключения» (B2.5)

`domains-block.tsx` расширяется из «Глобальных исключений» в **«Собственные домены и исключения»**:
- все добавленные пользователем домены со статусами **pending / approved / rejected** (лейблы: «На проверке», «Одобрен», «Отклонён»);
- существующие глобальные исключения (`domainBlocklist`) сохраняются как отдельная секция/тип записи (не терять текущую сущность);
- реестр — источник для комбобокса B2.4 и единственная точка, где видна судьба доменов;
- модерация — **на уровне аккаунта**, не per-campaign.

Расширить `AccountSettings`: добавить структуру пользовательских доменов со статусом и временем (`domainBlocklist` оставить для обратной совместимости или мигрировать в общую структуру с типом записи «исключение»). Писать через `settings_updated`/новые действия.

### 4. Жизненный цикл модерации — прототип (B2.6)

- Добавлен новый неизвестный домен → **pending**, стартует таймер (паттерн `campaign_phase_advanced`/`checkDomainAvailability`).
- По таймеру — **смешанный исход**: часть pending → **approved**, часть → **rejected** (симуляция).
- Таймер стартует **при добавлении** (аккаунт-уровень, независимо от запуска кампании).
- Кампания лишь отражает текущий статус (см. решение о едином источнике).
- Действие таймера — новый reducer-action (напр. `domain_moderation_resolved`), диспатчится из `setTimeout`, смонтированного там, где живёт реестр/настройки (или глобально при наличии pending-доменов).

### 5. Судьба доменов в описании (B2.7)

В `graph-description.ts`, на этапе **скоринга** (стадия `start`), если у триггеров ноды есть pending-домены, дописать отдельную строку:
- какие домены **ушли на модерацию**;
- **не прошедшие модерацию в кампанию не войдут**;
- после модерации: **одобренные подключаются, отклонённые удаляются из кампании**.

Текст детерминированный (обход графа + статусы из реестра), без LLM. Формулировка (RU): «Домены `<...>` отправлены на модерацию — в кампанию войдут только одобренные; не прошедшие проверку не подключаются, отклонённые удаляются из кампании».

Это требует, чтобы `describeWorkflow` получал доступ к статусам добавленных доменов (из `Campaign.triggerConfig` + реестра). Прокинуть их аргументом в `describeWorkflow` (сейчас `(graph, templates)`), не нарушая чистоту функции (статусы как вход, не как побочный эффект).

## Критерии приёмки

1. «Добавить свой домен» — комбобокс: ранее занесённый (сразу активен) или новый.
2. Новый неизвестный домен → pending-чип (жёлто-оранжевый, часы, без подписи) + запись pending в реестре; известный (в `knownTriggerDomains` / ранее одобренный) → сразу зелёный. Rejected в карточке триггера не показывается.
3. Реестр «Собственные домены и исключения» показывает pending/approved/rejected (лейблы «На проверке»/«Одобрен»/«Отклонён»); по таймеру часть pending → approved, часть → rejected. Глобальные исключения не потеряны.
4. Статус домена берётся из одного источника (реестр); на карточке/в описании он совпадает и не разъезжается на таймере.
5. На этапе скоринга в описании — строка о судьбе pending-доменов (уходят на модерацию; одобренные подключаются, отклонённые удаляются).
6. Судьба домена durable на сессию: добавленные домены и их статус доступны на карточке и в описании после навигации карточка↔граф↔оплата (не reload).
