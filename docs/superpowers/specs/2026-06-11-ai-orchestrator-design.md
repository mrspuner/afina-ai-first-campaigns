# Живой AI в Афине: оркестратор с инструментами

**Статус:** дизайн утверждается
**Дата:** 2026-06-11
**База:** ветка `feat/plans-001-003` (планы 001–003 DONE; спайк 002 дал работающий срез `/api/ai/workflow-ops`)
**Предшественник:** `docs/ai-workflow-integration-spike.md` — этот документ развивает его архитектуру с одного эндпоинта до оркестратора

---

## 1. Цель

Заменить mock-слой «AI» (regex-парсеры и канированные ответы) настоящей LLM по всем основным поверхностям интерфейса:

1. **Граф воркфлоу полностью** — правки операциями и пересборка с нуля, с контекстом текущего графа (снимается ограничение спайка `nodes: []`);
2. **Параметры нод** — правки свободным текстом при выбранной ноде;
3. **Триггеры в визарде** — add/exclude доменов свободным текстом;
4. **Свободные ответы по данным** — AI сам пишет ответы на вопросы о кампаниях/сигналах/статистике на основе реального стейта (решение оператора: генерация, не маршрутизация к канированным ответам);
5. **Конфигурация статистики** — свободная фраза → патч живой таблицы;
6. **Навигация** — «покажи кампании» → переход.

Вне скоупа: welcome-чат (остаётся скриптованным онбордингом), настройка шагов визарда кроме триггеров (AI отвечает навигационно), стриминг, авторизация и серверное хранение.

## 2. Архитектура: один оркестратор, инструменты, клиентский контекст

```
PromptBar (любой экран)
   │
   ▼
prompt-composer ── собирает запрос:
   │   { text, history, context: { screen, graph?, selectedNode?,
   │     wizardStep?, dataSummary } }
   ▼
POST /api/ai/assist  (Next.js route handler — единственный владелец ключа)
   │   системный промпт из 4 слоёв (§3)
   │   + инструменты, отфильтрованные по экрану (§4)
   │   generateText({ model: google("gemini-2.5-flash"), tools, ... })
   ▼
Gemini 2.5 Flash (stateless; ключ — Google AI Studio, free tier)
   │   ответ = вызов инструмента(ов) со строго типизированными аргументами
   ▼
клиент диспатчит результат в СУЩЕСТВУЮЩИЕ аппликаторы
   (applyOps / paramsPatch / триггер-дельта / stats_apply_patch / чат)
```

Принципы (унаследованы от спайка 002 и подтверждены оператором):

- **AI заменяет парсеры, не аппликаторы.** Каждый инструмент возвращает тип, который сегодня выдаёт соответствующий regex/matcher; пайплайн применения не меняется.
- **Интент определяет модель, но в пространстве, ограниченном интерфейсом**: клиент сужает набор инструментов по экрану — модель физически не может вызвать неприменимое здесь действие.
- **Stateless везде.** В Google ничего не «загружается»: знания, контекст и история уезжают внутри каждого запроса и забываются после ответа. Vercel-функции не хранят состояние. Стейт и память — в браузере посетителя; пользователей и авторизации нет (решение оператора), каждому браузеру — своя Афина.
- **Regex и канированные ответы — постоянный офлайн-fallback**, не временный костыль.

## 3. Промпт — четыре слоя

| Слой | Содержание | Источник | Меняется |
|---|---|---|---|
| 1. Роль и голос | «Ты — Афина: уверенная, точная, ненавязчивая; магия скрыта» | PRODUCT.md | редко |
| 2. Знания о продукте | сущности, карта интерфейса, границы, словарь (§5) | `src/lib/ai/afina-knowledge.ts` | в PR вместе с продуктом |
| 3. Контекст момента | экран; ноды графа (id, label, тип); выбранная нода; шаг визарда; сводка данных; история чата | собирает клиент | каждый запрос |
| 4. Инструменты | zod-схемы доступных действий | фильтр по экрану | каждый запрос |

Объём полного промпта ~5–7K токенов — меньше процента окна модели; free tier ограничивает частоту (~15 запросов/мин на ключ, общий на всех посетителей), не размер.

## 4. Инструменты

| Инструмент | Аргументы (zod) | Аппликатор | Доступен |
|---|---|---|---|
| `edit_workflow` | `ops: StructuralOp[]` | `applyOps` (есть) | редактируемый воркфлоу |
| `rebuild_workflow` | полный набор нод и рёбер | **новый**, через валидатор (§6) | редактируемый воркфлоу |
| `edit_node_params` | патч параметров ноды | путь `deriveParamsPatch` (есть) | воркфлоу + выбрана нода |
| `edit_triggers` | `{ add: string[], exclude: string[] }` | `applyEditToDelta` (есть) | шаг триггеров визарда |
| `configure_stats` | патч таблицы (rows, sort, period, rowCount) | `stats_apply_patch` (есть) | везде |
| `navigate` | цель из закрытого enum (разделы + кампания/сигнал по имени) | dispatch view (есть) | везде |
| `answer` | текст ответа | чат-панель | везде |
| `clarify` | 1–2 вопроса | чат-панель | везде |

Гарантии «не выдумает»:
- модель может вызвать только зарегистрированный инструмент; аргументы валидируются zod-схемами (невалидно → fallback);
- `navigate` — enum: несуществующий экран невозможен;
- `rebuild_workflow` — дополнительно валидатор графа до применения;
- `answer` — мягкая гарантия: граундинг сводкой реальных данных + правила знаний (§5) + экзамен (§10).

Составные просьбы («открой статистику и покажи по каналам»): модель возвращает последовательность до двух вызовов, клиент исполняет по порядку — работает, когда оба действия глобальны (navigate + configure_stats). Правка графа с чужого экрана невозможна (граф живёт в стейте своего экрана): поведение — `navigate` + ответ «Открыл черновик — скажите здесь, что поменять».

## 5. База знаний — `src/lib/ai/afina-knowledge.ts`

Один курируемый файл ~3–4K токенов, инлайнится в системный промпт. RAG/векторная база осознанно не нужны: корпус карманного размера, файл в репо = версионирование и ревью.

Разделы:
1. Что такое Афина, для кого (один абзац);
2. Сущности и связи: сигнал → триггеры (домены) → сегмент → кампания → воркфлоу;
3. Карта интерфейса: разделы, 8 шагов визарда, что где настраивается;
4. **Границы**: чего Афина не умеет (нет интеграций, нет экспорта, …) — на запрос за границей честное «этого пока нет», без выдуманных кнопок и без отсылок к чужим продуктам;
5. Правила ответов: 1–3 предложения, голос продукта, «магия скрыта» (внутренности не объяснять), не уверен — спроси или признайся;
6. Словарь пользователя: «сообщения» = смс/пуш, «письма» = email, «звонки» = IVR, «контактная политика» ≈ задержки/условия (отдельной сущностью не делаем — решение оператора уточнить при необходимости);
7. Чеклист уточняющих вопросов для сборки: во что конвертируем? какие каналы? как быстро/настойчиво?

Источники дистилляции: `docs/` (interface-overview, interface-flows, wiki, onboarding-flow, triggers-model-prototype, signal-flow-konfiguratsiya), PRODUCT.md, каталог `informational-replies.ts` (его факты вливаются в знания; сам каталог остаётся офлайн-fallback'ом).

## 6. Правила трёх уровней (ключевое решение)

Оператор зафиксировал: эталонных воркфлоу нет, маркетинговые «правила» выдуманы, пользователь может намеренно их нарушать. Поэтому:

| Уровень | Примеры | Кто следит | Жёсткость |
|---|---|---|---|
| **Механика** | есть вход-сигнал; терминалы «успех» и «конец» существуют и достижимы; condition даёт две ветки; нет висящих нод | расширенный `validateWorkflow` — **до** применения rebuild | блокирует |
| **Дефолты** | пауза ~1 день и параметры нод из шаблонов — только там, где пользователь не сказал | промпт: «заполняй пробелы, не навязывай» | мягко |
| **Воля пользователя** | «три смс подряд без пауз» — значит ровно так | промпт: «явное пожелание всегда побеждает» | суверенна |

Канон формы — «дерево-процессор» (формулировка оператора): слева сигнал-вход, в середине логические блоки (каналы, сплиттеры, паузы, условия), справа подводка к двум исходам. Зашивается как формат: в промпт (+1 пример валидного графа из `workflow-templates.ts` — учим формату, не вкусу), в валидатор, в экзамен. Маркетинговое наполнение — от пользователя через уточнения. Недозаполненные параметры → существующий механизм `needsAttention` (нода применяется с пометкой «требует внимания»).

Валидатор не прошёл → честный ответ «не получилось собрать», граф не тронут.

## 7. Поведение: три исхода, четвёртого нет

1. **Понял** → применил сразу + проговорил в чате, что именно сделал («Убрал СМС из цепочки — после паузы теперь сразу письмо»);
2. **Размыто/неоднозначно** → `clarify`: **один раунд, максимум 2 вопроса** (решение оператора); ответы связываются историей; после сборки допущения проговариваются («Собрал из расчёта 3 касания за неделю — поправьте, если иначе»);
3. **Не понял** → честное «не понял, скажите иначе».

Запрещённый исход: молча сделать не то. Понимание перефразировок («хочу чтобы сообщения не использовались» = удалить смс) обеспечивают: семантика LLM + граф в контексте (резолвит «сообщения» в конкретные ноды) + словарь знаний + `clarify` при реальной неоднозначности.

## 8. Откат (решение оператора: применять сразу + возможность вернуть)

- Перед применением AI-операции над графом (`edit_workflow`/`rebuild_workflow`) — снапшот графа в стейт (`lastAiSnapshot`);
- После применения в suggestion-bar промптбара появляется подсказка «↩ Откатить» (существующий механизм `selectPromptSuggestions`); фразы «откати», «верни как было» понимает и оркестратор;
- Срабатывание → граф восстанавливается из снапшота, подсказка гаснет. Глубина — 1 шаг (последнее AI-действие); стек — следующая итерация.

## 9. Память сессии

История чата уже живёт в `chat-context`; последние ~8 сообщений уходят с каждым запросом — это носитель и уточнений (§7), и связности («а в мае?» после вопроса про июнь). Сбрасывается со сменой раздела вместе с контекстом экрана (существующее поведение). Долгосрочной памяти и идентификации пользователей нет осознанно.

## 10. Экзамен (eval-набор)

Проверяет **послушность, форму и честность — не маркетинговый вкус** (кейса «пауза некрасивая» не существует; «три смс подряд» — кейс на соблюдение).

Устройство:
- `evals/cases.ts` — кейсы «фраза + контекст → ожидание» (какой инструмент, что в аргументах, прошёл ли валидатор, наличие/отсутствие ключевых фактов в тексте);
- `scripts/run-evals.mjs` — прогонщик: шлёт кейсы на `localhost:3001/api/ai/assist`, сверяет, печатает счёт. AI участвует только в момент прогона;
- запускается вручную (`npm run eval`), НЕ в CI: нужен ключ, тратит квоту, ~5 мин на 50 кейсов.

Моменты запуска: при разработке оркестратора (основной цикл «обучения»: провал → правка знаний/промпта → прогон); перед коммитом изменений AI-слоя; перед демо; после коридорного теста (новые кейсы из реальных фраз); при смене модели.

~80% кейсов готовится заранее из сырья в репо: фразы из `structural-commands.test.ts` (нижняя планка: AI понимает всё, что понимал regex), 10 запросов `stats-query-matcher`, 40 записей `informational-replies`, 36 сценариев `scenarios.ts`, ловушки из дизайн-сессии (косвенные фразы, суверенность, вопросы про чужие продукты). Перефразировки генерятся LLM и отбираются руками.

**Журнал для сбора данных (новый узел):** dev-флаг `afina.dev.aiLog` (по образцу `afina.dev.*`); при включении каждый обмен пишется в localStorage браузера (фраза → инструмент → исход), в дев-панели кнопка «Выгрузить журнал» (JSON). Журнал живёт только в браузере тестовой машины — privacy-граница сервера не двигается; по умолчанию выключен, не пишется ничего.

## 11. Fallback-цепочка (каждое звено — постоянная архитектура)

```
нет ключа (проба при старте) → всё как сегодня: regex + канированные ответы
ключ есть, но 429 / таймаут 6с / сеть / невалидный ответ → regex + канированные
rebuild не прошёл валидатор → «не получилось собрать», граф не тронут
clarify / answer → не fallback, штатный диалог
```

E2E-тесты идут по пути «нет ключа» — поведение бит-в-бит сегодняшнее.

## 12. Latency-UX

Существующий цикл «Думаю…»: старт сразу при сабмите, минимум 1.5с, максимум до прихода ответа. Ответы `answer`/`clarify` — в чат-панель с маскотом (AI-индикация по PRODUCT.md). Стриминг — осознанно вне итерации.

## 13. Privacy

На сервер (и далее в Google) уходит: текст фразы, история чата (~8 сообщений), сводка графа (id/label/тип нод), компактная сводка моковых данных (кампании с метриками, сигналы, агрегаты статистики), позиция в интерфейсе. Все данные приложения — моковые; чувствительного контента нет (подтверждено оператором). Ключ живёт только в `.env.local`/env Vercel, в клиентский бандл не попадает. Тексты фраз на сервере не логируются (журнал §10 — клиентский, под флагом).

## 14. Что НЕ трогаем

- Аппликаторы: `applyOps`, dispatch-пайплайн, анимации цикла;
- Regex-парсеры и matcher'ы — fast-path/fallback;
- `informational-replies.ts` — офлайн-fallback (факты вливаются в знания);
- Welcome-чат — скриптованный онбординг;
- Эндпоинт спайка `/api/ai/workflow-ops` — живёт, пока оркестратор не покроет его кейсы; поглощается в конце, не в начале.

## 17. Решения оператора, принятые в этой сессии

| Вопрос | Решение |
|---|---|
| Скоуп | все 4 поверхности + статистика + навигация |
| Форма ответов по данным | AI генерирует сам из сводки стейта |
| Глубина перестройки графа | ops с контекстом + rebuild отдельной операцией |
| Архитектура | оркестратор + инструменты (tool calling), не per-surface промпты и не LLM-роутер с union |
| Пользователи/авторизация | не нужны — стейт в браузере |
| Маркетинговые правила | не enforce'ить; механика — валидатором; воля пользователя суверенна |
| Размытый запрос на сборку | 1 раунд уточнений, максимум 2 вопроса, затем сборка с допущениями вслух |
| Применение правок | сразу, с откатом и подсказкой «Откатить» в промптбаре |
| Канон формы графа | «дерево-процессор»: сигнал → логические блоки → исходы |
